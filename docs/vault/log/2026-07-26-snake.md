`snake` — 16x16 Snake on the [[LM-75 Display]], 5 public cases, tick cap 15,000,000,
[[Rounds|round-based]] with frames gating input. We scored **zero** on it: `py/snake_gen.py`
emitted a loadable 177x115 grid that step-capped 0/5 with **0 frames** on every case.

## Inherited architecture (`py/snake_gen.py`)

Five rooms, seven pipes, three little men:

- **IN** — input room, pipe into HUB.
- **BRAIN** — the whole game as a compiled control-flow graph (`BLOCKS`) laid into one room by the
  `Brain` class, with an auto-router (`wire_order`) for the back edges. Exactly one pipe in and one
  out, so every `r`/`s` is unambiguous.
- **HUB** — ring turnaround plus router. Reads a token from the ring and dispatches on it:
  `<1000` ring data (echo back to BRAIN), `==1000` draw prefix, `==2000` fetch input,
  `==3000` fetch input and multiply by 16.
- **DRAW** — 1 in, 3 out (ADDR / DATA / SWAP); payloads arrive in pairs.
- The display, 16x16.

Game state lives in the ring as `[V...] DX HX DP HP F B1..BL 0`.

## 12:10 — decision: build on it, do not restart

Reproduced `0/5` exactly (`lmr test`, all five cases step-cap at 5,000,000 with 0 frames matched).

## 12:25 — hypothesis, and it was right

> **Hypothesis**: a return path in one of the small hand-written rooms walks onto the `@` and has no
> instruction there to turn it back into the loop.

`lm run -i "3 3 0 0" --ticks 400 --trace` settles it in one command. The HUB man completes exactly
one useful lap and then dies at t=210:

```
t=00210 (135,7) S A=3 B=1000 BP=0 'v'
t=00211 (135,8) S A=3 B=1000 BP=0 'v'
t=00212 (135,9) S A=3 B=1000 BP=0 '@'
t=00213 (135,10) N A=3 B=1000 BP=0 '^'
t=00214 (135,9) N A=3 B=1000 BP=0 '@'
t=00215 (135,8) S A=3 B=1000 BP=0 'v'      <- bounces here forever
```

`@` is a **no-op when you step on it**, not a turn. HUB's column 1 was drawn as `v v @ ^ ^ ^ ^ ^ ^`:
returning men come *down* the column from row 2/3 and *up* the column from rows 5-10, both
converging on the `@` at local (1,4), which was supposed to restart the eastward loop. It doesn't.
Every one of HUB's four return paths (ring echo, draw prefix, input, input×16) ends in that same
three-cell `v`/`@`/`^` bounce.

Consequence: HUB never reads the ring again, BRAIN blocks forever on `r`, DRAW blocks forever on
`r`, and the run dies at the step cap having drawn nothing. One character.

**DRAW has the identical latent bug** — `@` at its local (1,2) with `v` above and `^` below, and all
three of its return paths (ADDR, DATA, SWAP) converge on it. It never got that far, so the trace only
shows it blocked on `r`.

Extracted to [[A spawn cell cannot close a loop]].

## The fix

The join cell must be a `>`; the `@` has to live somewhere that *feeds into* the join, and since a
man always spawns heading **east** ([[Rotating a room breaks its spawn]]) that means a short stub
that turns him onto the loop.

- HUB: `>` at local (1,4); `@` at (1,1), `v` at (2,1), `<` at (2,10) — the spawn walks east one cell,
  drops down column 2 (crossing the `` ` `` of the `1000` literal, which is a no-op vertically since
  column 2 holds no *pair* of backticks), turns west at row 10 and joins the existing `^` column.
- DRAW: `>` at local (1,2); `@` at (7,4) — spawn walks east into the `<` already at (8,4) and rides
  the existing westward row-4 return path into the join.

Neither change moves a wall or a pipe attachment, so all four `s` / `r` nearest-pipe resolutions in
HUB are untouched (checked by hand: the two outgoing segments sit at local `(4,-1)` and `(2,12)`, the
two incoming at `(8,-1)` and `(18,12)`).

Tried relaxing `emit`'s global column reservation — reuse is safe when the gap is empty,
since an empty vertical literal is a documented no-op. It is not safe here, and both
runners agree exactly:

```
error: expected a digit or a space between backticks, but found '<' at (23, 42)
```

The router delivers every back edge by running **west along the target's entry row all the
way to the spine**, laying `<` across the whole code area, and every block sits between
two such rows. So the reservation is forced by the wire routing.

Shortening the constants (`1000/2000/3000` -> `256/512/768`, sentinel split off to `-257`)
is the mechanical version. **13/13, footprint 64,009 -> 61,504, server 17/17 at
17,270,612,631.** Small, because `emit` reserves two columns per literal *whatever its
length* — width tracks the literal COUNT.

Also tried and abandoned, both defeated by the same non-crossing constraint:

- **merging the two apply chains** (the scan gadget and `@LOOP` leave identical state at
  the marker, so one shared `TAP` should work) — `TGROW1`'s back edge to `TAP` crosses
  `TCHK5`'s forward wire in every placement;
- **one game-over chain instead of three** — a three-way fan-in from different depths
  cycles above the chain and below it.

The duplication in `snake_gen3.py` is **forced by the router, not an oversight**, and it is
also what multiplies the literals: 53 of the 80 are inside the four repaint copies and the
three game-over copies.

## 17:45 — the display-skew fix

`snake-tight.man` passes **14/14** locally — five public cases plus nine scripted stress
cases including a 30-cell serpentine — and **13/17** on the judge, four wrong-frames. Its
pipe graph is structurally identical to the 17/17 grid: same rooms, same walls, same
ADDR/DATA/SWAP assignment. Only the **lengths** differ.

That points at [[Equalise the three display pipe lengths]]. The display applies ADDR
before DATA within a tick, so with lengths `La` and `Ld` the driver must leave `La - Ld`
ticks between the two sends. The layout shipped `La = 43`, `Ld = 4` — **39 ticks of margin
nobody had written down**, which held only because HUB upstream takes ~55 ticks a token.
Any repack that lets payloads bunch up in the HUB→DRAW pipe drops the gap to DRAW's own
loop time (~15) and the pixel lands at the previous cursor position.

Re-routed so ADDR runs north of the display and DATA folds south of it — they cannot cross,
and they come out **20 and 22 cells**. With `La <= Ld` the constraint reduces to "sent in
the right order", which DRAW guarantees, and no repack can break it.

14/14 local, **17/17 on the server**, score unchanged at 17,270,612,631. Re-shrinking from
this base is the test of whether the hypothesis was right.

## 2026-07-26 — round 3, fresh agent

Baseline `snake18.man`: 17/17, 694,124,069, 97x97 (BRAIN 57x95, 26 blocks).

### The fruit test was computed twice, so half of both apply chains was dead code

> **Hypothesis**: `TAP`'s `M r ~` branch re-decides something `TCHK5` already decided,
> so one arm of each `apply_chain` copy is unreachable.

Confirmed, `py/snake_gen19.py`. `TCHK5` tests `F XOR -(newHP+2)` and sends the head to
`TAPG` (ate the fruit) or, via the self-collision scan, to `TAPN` (did not). Lap 1 changes
neither `F` nor any of `DX/HX/DP/HP`, so when `TAP` recomputes exactly the same XOR in
lap 2 the answer is already fixed: **`TAPMG` and `TAPGN`, with a whole `PAINT` copy each,
could never be entered.**

Deleting the branch also deletes the XOR. `... M 2 - N M r ~` followed by `~ s` is
`... M 2 - N M r s`, because `B` still holds `T` either side of the pair — so each chain
goes from four blocks to two, and `apply_chain` takes a `tail` argument instead of
splitting.

**BRAIN 57x95 -> 57x73**, 26 blocks -> 20. The ring had to be re-routed (its old
attachment row, 90, is outside the room now) and is held at exactly 171 cells by solving
`2*DEEP - 3 = 171` for the excursion depth rather than by counting: same shape, one
rectangle instead of two, down x=58 and back up the free column east of the display.

14/14 local. Grid is **97x88** — the height is now 9 rows of slack and **width is the only
term that costs anything**. Score is ticks-only for this step.

Two things learned about the CFG router that the predecessor's notes did not have:

- **A branch can be inlined mid-row.** `a` falls through east when the backpack is clear and
  turns north when it is set, so it needs only a `>` on the row above — not an entry row,

A full repaint costs **four ring tokens per body cell** (`1 s` prefix, the ADDR payload,
`1 s` again, the colour) and each token is a HUB lap. A 30-cell snake spends ~130 tokens a
frame on drawing. Because the display's `SWAP 1` *preserves* the next buffer, a frame can
be incremental instead: **erase the vacated tail, paint the new head, commit** — ten tokens,
constant in snake length. That is a 3-5x tick cut, and it also deletes `PAINT` and `PAINTF`
outright (BRAIN 47x66 -> 47x58).

`py/snake_gen28.py` implements all of it and is **one encoding short of working**:

- `DRAW`'s payload arms are `p < 0 -> ADDR = -p-2`, `p = 0 -> SWAP`, `p > 0 -> colour p+2`.
- Erasing needs **colour 0**, which wants `p = -2` — and `-2` is a legal ADDR (cell 0).
  Colour 0 is simply not expressible. Everything else in gen28 is correct: `TAQ`'s move arm
  parks the head token in `B` and sends the prefix *before* the `r`, so the tail address is
  available without losing `T`; `JOIN` paints the head from `B`; `FRUITB` paints the fruit
  once at spawn; `INIT`'s first `SWAP 1` works because the next buffer starts empty.

The fix is a `DRAW` redesign, and the shape of it is forced. Body tokens must become
`-(addr+3)` so that `p = -2` is free for "black", `DRAW`'s constant becomes `3` (which also
turns the colours into the single digits `6` and `7` again), and its negative arm needs one
extra branch: `p = -2 -> colour 0`, else `ADDR = -p-3`. DRAW's interior is 9x6 and too tight
for that third stop, so it has to grow — which is free, since the band is 21 wide and DRAW
is 11, and only its three pin offsets and the rows below it have to be re-derived.

**Do that next.** It is worth more than every footprint change in this round put together.

### The next lever, worked out but not built: two laps per round instead of three

MAIN's whole lap exists to reach V, which arrives last because the input request is the last
thing issued before the record is re-sent. Issue the request as **the first send of the last
lap** and V arrives *before* the re-sent record, so MAIN becomes a five-cell branch (`1 M r -`
and an `X`) and the record is read by whichever block the branch picks. Worth ~1.33x.

Frame attribution is not a risk: [[grading#Rounds]] says the input for round N+1 is
withheld until round N's output is received, and frames are matched in order, so requesting
early only makes HUB wait. The SWAP tokens are already ahead of the request in the ring.

Three placements, two of them easy:

- **tick round** — VREQ goes at the top of `TAP`, which enters with `A = 0` from the scan's

  and that needs `T` alive after the collision scan. It is not: the grow arm parks `B = -1`
  as the scan sentinel and `TAQ` recomputes `T` in lap 2. Draw **before** the scan instead —

  tail. The erase-then-paint pair fits in the two arm rows the branch already owns, and
  `W` is what keeps `B = T` across it: `1 s W s W s 9 s 1 s 0 s` sends prefix, ADDR, prefix,
  colour, prefix, SWAP and leaves `B` untouched.
- **fruit round** — VREQ at the top of `FRUITB`, which enters with nothing live. Free.
- **direction round** — the hard one. `DIRB` enters with `A = -DX'` and `B = -DP'`, both live,
  and `DIRA` enters with `A = V-1`, `B = 1`. Loading the literal `2` to send it destroys the

  `B = 2`, which makes `DIRA` open `M 1 - N` instead of `-` — three more cells on the row
  that currently sets BRAIN's width, so it wants `DIRA` split again first.

**The rule is narrower than "issue the request as the first send of the last
lap".** What MAIN needs is for `V` to be the *first* token it reads, and a token
lands in the ring at the point HUB reaches it — so the VREQ has to sit
**between the second-to-last lap's record and the last lap's**. Either end works:
the last send of lap N-1 or the first send of lap N. And because a frame gates
the next input, the SWAP has to come before it. So the real constraint is

> commit the frame in the second-to-last lap, then VREQ, then the last lap's record.

MAIN is now `1 M r -` and an `X`. Five cells.

| --- | --- |
| tick | `TCHK5` draws in **both** arms and `TAP` SWAPs on the scan's clean exit |
| fruit | `FRUITA2` builds, paints and commits the new fruit at the end of lap 1 |
| direction | no frame at all — `M 2 s 1 W` on MAIN's cw arm is the whole change |
| INIT | the one round that still pays three laps (see below) |

### Painting the head before the collision is known is safe

The tick round's frame has to commit in lap 1, and `T` is live in `TCHK5` and
dead after the scan (the grow arm parks `B = -1` as the sentinel). So the draw
moves *before* the scan, which means the head is painted green before we know
whether the round is a game over. That is sound, and the reason is exact:

- a **wall** hit branches to `OVFB` from `TCHK`/`TCHK4`/`?OVFB`, all of which are
  upstream of any draw, so the buffer is untouched;
- a **self-collision** means the new head *is* a body cell, so `OVFA`'s red
  repaint covers the green pixel;
- and the `SWAP` that would publish it rides `TAP`, which is on the scan's clean
  exit only.

One real bug this design invites, caught by reasoning rather than by a case: the
move arm reads `B1` for the erase address, and if it does not **also echo it**
the game-over repaint has no tail token and draws that cell black. Hence
`1 s r s s` — one `s` to DRAW as the ADDR, one to the ring as the record echo.
`TSCAN` then loses its leading `r s` (B1 has already been echoed by the arm, and
on the grow arm `B = -1` so testing it costs nothing), and `TAQ`'s move arm
shrinks to `~ s r`.

### The next lever, and why the obvious one is blocked

**One lap per tick round.** The headers can be rewritten *speculatively* — a
game over halts the man and the red repaint only reads the body — so the only
thing forcing two laps is the tail: on a move `B1` must leave the record, but a
self-collision discovered later in the same body needs it back, and the
backpack cannot give it back (`b` writes, `d`/`a`/`x` branch, `q` overwrites —
**there is no read**). Two ways out, both real work:

1. **A `Q` field.** Keep `B1` in the record, erase its pixel, and set a
   "the front body token is stale" flag; every handler opens with a conditional
   `r` that drops it. One extra token a lap and three `cond` rows.
2. Head-first body order, which moves the tail to where the verdict is known —
   but then the scan needs a one-token lookahead and there is no third register.

Either way it **also needs the input to bypass the ring**, because with one lap
the VREQ can never precede the record: the frame commits at the end of the lap.
The input room may have only one outgoing pipe, so that means pointing it at
BRAIN instead of HUB — and then BRAIN has two incoming pipes and every one of
its ~50 `r`s binds by distance. That is tractable **only** because both would
attach to BRAIN's east wall, where the `(42 - x)` term cancels and the bisector
is a horizontal line: with input at MAIN's code row and ring-in four rows below,
every `r` on rows <= 9 takes the input and every `r` on rows >= 11 takes the
ring. INIT and MAIN are the first two blocks, so that falls out of the existing
order. HUB then loses commands 2 and 3 and gets faster again.

### 2026-07-27 — direct table shift: 59x60, 75,085,412

The west-running DIRB hypothesis was overcomplicated. A prototype did execute DIRB right-to-left

M 8 * M TABLE }
