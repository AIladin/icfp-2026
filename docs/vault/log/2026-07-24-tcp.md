# tcp — Packet Reassembly (Semester 2)

## Spec TL;DR

Round 1 delivers `n` then the first packet `seq val`; every later round one packet `seq val`,
scrambled. Output values in `seq` order, as early as possible: keep a `want` pointer, buffer
out-of-order packets, and drain the longest run starting at `want` each time it unlocks.
If a packet arrives with `seq >= want + 16`, output `-1` and stop.

- `1 ≤ n ≤ 48`, `0 ≤ seq < n` distinct, `1 ≤ val ≤ 999`.
- **6 public, 0 private** — local score is the *whole* score. Cases: in-order n=6 (6 rounds),
  max-displacement swap (17), drain burst (16), loss case (16), shortest n=1 (1),
  block-reversed n=32 (32).
- scoring `footprint-tick` = `max(w,h)² × avg ticks`. tickCap null → 5M.

## Design (v1)

**Variable-length slot ring.** Window is 16, so a 16-slot buffer indexed by offset from `want`
suffices. The ring is a pipe loop HEAD→TAIL→HEAD carrying tokens

| token | meaning |
| --- | --- |
| `-1` | marker: end of the *known* slots. Everything past it is implicitly empty. |
| `0` | empty slot |
| `v>0` | slot holding value `v` |

Invariants: slot 0 (= `want`) is always empty at round start; trailing empties are never stored,
so the ring shrinks as the window drains. Capacity ≤ 16 slots + marker = 17 tokens.

HEAD holds `want` in **B** permanently (`r`/`s`/`X`/`m`/`b`/`d` never touch B), BP is the loop
counter, A is the token. That is exactly [[One persistent register per room]] satisfied.

Per round, **exactly one lap**:

- `r` seq; `A -= B` → `d`; `b ]]]] d` → if `d>>4 > 0` emit `-1` and halt; `X` on `d`.
- `d > 0` (INSERT): `b` → BP=d. WALK d tokens (r,s,m). If the marker turns up early, ZEROFILL the
  remaining BP slots with `0`, then write, then re-emit the marker. Otherwise overwrite slot `d`
  and PASS the rest until the marker.
- `d == 0` (DRAIN): read `val`, emit it, `want++`; drop old slot 0; then read tokens: `>0` → emit +
  `want++`, `0` → that is the new slot 0, re-send it and PASS to the marker, `<0` → ring empty.

No `want` needs to be recomputed and no shifting happens, because the marker delimits the live
prefix and the drained tokens are simply *not* re-sent.

### Why not the alternatives

- **Fan of 16 addressable pipes** ([[Pipe fan stack]]): 16 pipes = ≥16 rows of bounding box,
  ~484 footprint before routing. Ticks would be lower (~60/round) but footprint is squared.
- **Fixed 16-slot ring** (no marker): draining `k` slots needs `k` zeros appended *before* the
  marker, and BP cannot count up — two counters, one backpack. The variable-length prefix dodges
  it entirely.
- **Sorted (seq,val) pairs**: O(1) insert, but sorted insert needs `new_seq` in B *and* `want` in
  B. Would need a third room.

### Pipe banding

HEAD has four pipes, all on its **south** face, so only the column decides
([[Nearest pipe resolution]]). Order along the wall: input(in) 2, output(out) 6, ringout(out) 12,
ringback(in) 14. Incoming boundary at 8.5, outgoing at 9.5, which leaves three bands:

| cols | `r` | `s` |
| --- | --- | --- |
| 1–8 | input | output |
| 9 | ring | output |
| 10+ | ring | ring |

The middle band is exactly what the drain's "read a stored value, emit it" step needs.

## Where the ticks go, and why v1 cannot reach rank 1

Target is `best` 505 172. The reachable pairs are footprint 484 → 1 045 server ticks, 400 → 1 264,
289 → 1 748. v1 sits at 1 089 × 6 495.

Two independent problems, both structural:

1. **Every loop cycle is 15–17 ticks, against a floor of 6.** The WALK body is
   `d, r, X, merge, s, m` — six instructions — but the return riser is eight cells, so the cycle
   is 17. Same for PASS (15) and the drain loop (17). A 3×4 clockwise ring gets this to 10:
   `d`(entered heading north) `r` `.` `v` / `X` `v` / `<` `<` `s` `^` `m`, with `X`'s
   *straight* and *clockwise* exits merged on a single `<`. `X` and `d` both turn, so they pay for
   two of the four corners.
2. **The slot ring is O(L) per round even when only one packet is pending.** Storing *slots*
   (value-or-zero indexed by offset) means one arrival at offset 15 forces `L = 16` and every
   later round walks all 16 tokens. On `single max-displacement swap` that is 3 240 ticks to move
   17 packets.

### v2, designed but not built: sparse `(seq, val)` pairs

Store only the packets actually pending, as **two tokens each**, unsorted, with the `-1` marker
delimiting the tail. Nothing is indexed by offset, so nothing shifts.

- **INSERT is O(1) and needs no lap at all**: `s` seq, `r` val, `s` val. Sends append at the tail;
  the marker is re-sent last on every drain lap, so an append landing "after" the marker is still
  ahead of it in the next lap's cycle order. ~40 ticks, no BP, no `ZEROFILL`, no `WALK`.
- **DRAIN** laps the ring comparing each stored `seq` against `want` (in **B**): `r`, `-`, `X`;
  no match → `+` `s` `r` `s`; match → `r`, `s` to output, `1 W + M` to bump `want`, and `1 b` to
  flag "drained". At the marker, `s` it and `d` on the flag: relap or return to MAIN.
- Cost model: unsorted means a descending arrival order costs one lap per drained value, so
  `drain burst` is ~2 400 ticks — but `in-order`, `max-displacement` and `loss` collapse to
  ~40 ticks a round because the ring is empty or holds one pair. Estimated local mean **~1 560**
  against 3 879, i.e. **2.5×**.
- Cost: the ring must hold `15 pairs × 2 + marker = 31` tokens, so ~32 pipe cells instead of 19.
  Pipe cells fold, and folding only moves the bounding box ([[Delay line ring]]).

v2 + 10-tick loops ≈ 1 730 server ticks. At footprint 324 that is ~560 K, at 289 ~500 K — i.e.
**rank 1 is reachable, but only if the whole program fits in ~18×18**, which needs the layout
packed by hand rather than laid out block-per-row-band as v1 is.

### The alternative that was rejected

A **fan of 16 addressable pipes** ([[Pipe fan stack]]) keyed on `seq mod 16` gives genuinely O(1)
rounds — WRITER navigates to a slot with a 4-deep `b`/`x`/`]` bit-trie in ~8 ticks, READER walks
its lane monotonically so draining is amortised one slot per packet. It was rejected because
**16 pipes need 16 distinct rows (or columns), so the bounding box starts at ~20 before any
control logic**, and footprint is squared. It also needs `want` shuttled from READER to WRITER
every round for the loss test, since neither man can hold both `want` and the address.

If v2's tick estimate holds but the packing cannot get under ~20×20, the fan becomes the better
trade — it is the design to try next after v2.

## Remaining gap and the levers, in order of value

Server 4 320 154 against `best` 505 172 — **8.5× off**. Both terms have to move.

1. **Sort the ring** (≈1.9× on ticks). Unsorted means `k` drains cost `k` laps; sorted makes the
   whole drain one lap. Blocked on registers: the scan needs `new_seq` in **B** and `want` is
   already there ([[One persistent register per room]]). The fix is a third room used purely as a
   register — HEAD parks `want` there for the duration of the insert lap and reads it back, two pipe
   hops (~12 ticks) against ~9 ticks per token saved. Estimated local mean 3 452 → ~1 830.
2. **Compact HEAD** (≈1.8× on footprint). HEAD is 21 of the 28 rows and is laid out one basic block
   per row band, which is legible and wasteful; the loops are 18–22 ticks per pair where the floor
   is ~8. A hand-packed HEAD at ~14 rows takes the whole program to ~21×21 = 441.
3. Together: 441 × ~2 900 server ticks ≈ **1.28 M** — still 2.5× short, so a third idea is needed on
   top. The honest candidate is the [[Pipe fan stack|16-pipe fan]] with a `b`/`x`/`]` bit-trie
   decoder: genuinely O(1) rounds (~50 ticks) at a footprint that starts near 20×20 because 16 pipes
   need 16 rows. That trade only pays if the per-round cost really lands near 50, which it should,
   since nothing in it scans.

The greedy shrinker (`scratchpad/tcp/shrink.py`) is worth keeping for other problems: it deletes one
row or column at a time, re-runs `lmr test --json`, and keeps the deletion if the program still
passes and does not score worse. It found 4 rows on v1 and 1 on v2 — dense two-dimensional routing
has few free rows, unlike the tall thin layouts where [[Empty rows are free to delete]] pays.

### Measured: the drain cycle is 32 ticks per pair, and 21 of them are travel

Counting the v2 DLAP/NOMATCH cycle cell by cell: `> r X` `-` `X` `+ s r s` `v` is eleven working
cells, and the return — row 16 west, the column-2 riser, row 13 east — is **twenty-one**. The riser
sits at column 2 only because MATCH and NOMATCH both had to reach it, and everything between is
`.` padding.

That is the single largest remaining tick lever and it is pure layout: a riser adjacent to the loop
would take the cycle from 32 to ~15, i.e. **~2× on the reversed cases**, which are the ones that
dominate the mean. It is blocked on column pressure — `s` needs `c ≥ 11` and the loop already spends
c11/c12/c13 on `s r s`, so the riser has nowhere to sit without first moving MATCH out of rows 16-17.
Same lesson as [[Bounded loop with the backpack#Cost]]: **loop cost is the perimeter, not the
instruction count**, and here the perimeter is two-thirds padding.

## v3 — 10-tick drain loop, squared box: server 1,231,184 (20/20)

`py/tcp_build3.py`, **21x20, server 1 231 184 = 441 x 2 791.8 ticks, 20/20**. 3.5x on v2.

| build | footprint | local ticks | **server** |
| --- | --- | --- | --- |
| v2 pair ring | 784 | 3 452 | 4 320 154 |
| **v3 fast loop** | **441** | **1 837** | **1 231 184** |

Three changes, all layout, none algorithmic:

1. **The drain loop is now a 3x4 rectangle whose every cell does work.** 10 ticks per stored
   pair against v2's 32. The trick that closes the last two corners is using `X` *as* a corner:
   the west lane ends `s`(seq) `r`(val) `X`, and `X` turns clockwise because `A = val >= 1`
   always — so the turn is free, and the `s`(val) sits on the riser itself.
   Cycle: `> r - X` / `+` / `< s r X` / `s`. See [[Register bands cost ticks]] — the whole loop
   fits inside the ring-`s` band (c<=13) and the ring-`r` band (c>=9), which is what makes it packable.
2. **INSERT and DRAIN unified.** Every round now pushes `(seq,val)` into the ring and only *then*
   branches; the drain lap finds the arriving packet like any other. Deletes the whole
   "emit directly from MAIN" path. Costs 2 extra ring tokens of capacity (33, not 31).
3. **Squared the box.** 19x28 -> 21x20. Footprint is `max(w,h)^2`, so the tall thin v2 was paying
   for 8 rows of pipe snake. The ring's 33-cell capacity now lives in two columns *beside* HEAD
   rather than in rows below it.

Registers unchanged: `B = want` permanently, `BP` = the loss/branch/drained flag, `A` = token.

### Where the remaining ticks are — it is NOT latency

Measured directly: rebuilt with the ring cut from 35 cells to 22 and ran the cases that fit.
`in-order` went 843 -> 739 ticks, i.e. **13 fewer ring cells bought 12%**, ~1%/cell. So a lap is
*work*-bound, not latency-bound, and the two-ring split (seq ring + val ring, ~17 cells each)
that would halve latency is **not worth building** — it would buy ~15% for a 6-pipe HEAD.

The real number: `in-order` costs ~140 ticks/round, of which only ~45 is lap latency. The other
~95 is **fixed travel between basic blocks**:

| lane | ticks | why it is long |
| --- | --- | --- |
| MAIN east+west | 26 | must reach input-`r` (low c) *and* ring-`s`, then come back |
| drain entry | 15 | MAIN's branch is at c2, the loop entry is at c9 |
| marker exit -> MAIN | 16 | marker branch is at c13, MAIN entry is at c2 |
| MATCH -> loop entry | 18 | output-`s` needs c>=14, loop entry is c9 |
| relap | 10 | |

Every one of these is a band crossing: the lane is long *because* `r` and `s` resolve by column.
This is [[Register bands cost ticks]] at the level of the whole program rather than one loop —
same lesson the plotter and brackets agents hit, one scale up.

### What to do next, in order

1. **Re-site the pipes so MAIN and the loop share a band.** The blocker is that MAIN needs
   input-`r` + ring-`s` while the loop needs ring-`r` + ring-`s`, so input and ringback must be
   column-separated, which forces MAIN and the loop apart. **Putting the output pipe on HEAD's
   north wall** frees the column axis for the other three and could collapse three of the five
   lanes above. Worth ~1.5x and it is pure layout.
2. **Sort the ring** (still ~1.9x, still needs a third room to park `want` — and now also to park
   `val`, because with `B = new_seq` during the insert lap there is no readable register left for
   `val`: `BP` is write-only). A PARK room is a two-cell echo (`r`,`s`) and its return pipe doubles
   as a one-slot FIFO, so `s val ; s want` then `r val` at the insert point and `r want` at the end
   works without any [[A delay line is the only way to gate a pipeline|gating]].
3. Only then the 16-pipe fan.

### Correctness harness

`py/tcp_fuzz.py` generates 91 cases in `icfp tests` JSON shape: hand-built edge cases (n=1, n=48
in-order and fully reversed, `seq == want+15` legal vs `seq == want+16` loss, loss *after* `want`
has advanced, window-full-then-release) plus 40 random permutations and 40 never-lossy scrambles
built by only ever choosing from `[want, want+15]`. v2 and v3 both pass 91/91. Run it after every

## v5/v6 — 20x20 box and one marker lap per round: server 1,052,800 (20/20)

`py/tcp_build6.py`, **20x20, server 1 052 800 = 400 x 2 632.0 ticks, 20/20**. Rank 9 -> 7.

| build | footprint | local mean | fuzz | **server** |
| --- | --- | --- | --- | --- |
| v3 fast loop | 441 | 1 837 | 131/131 | 1 231 184 |
| v4 (HEAD relaid, same box) | 441 | 1 755 | — | not submitted |
| **v5 (20x20)** | **400** | 1 783 | 131/131 | **1 085 160** |
| **v6 (one marker lap)** | **400** | **1 710** | 131/131 | **1 052 800** |

Three changes, all still pure layout / control flow — the ring algorithm is untouched.

1. **HEAD re-laid-out into 10 interior rows instead of 12.** The MATCH tail no longer walks the
   east wall down to a return lane *below* the loop; it turns north one row above it and comes back
   west doing `W + M 1 b` on the way — [[Register bands cost ticks|the return leg carries the work]].
   MATCH-to-loop-entry went 18 ticks to 12. Row order top-down is now
   INIT/LOSS, MAIN-east, MAIN-west, exit-lane, drain-entry, marker, MATCH-return, loop x3.
2. **Squeezed to 20x20 (fp 441 -> 400).** HEAD is 18 wide (cols 0-17) with `output` moved from
   south c17 to south c16; the ring riser is a 2-column hairpin at c18/c19. The hairpin is not
   decoration — the ring *needs* 33 cells of capacity (15 buffered pairs x 2 + the arriving pair +
   marker), so pipe length is a correctness constraint, not just latency.
3. **The marker is pushed at drain entry, not re-sent on exit.** v3 saw the marker three times per
   round (entry with the flag pre-set, after the match, and the exit lap). Now MAIN pushes
   `seq,val` and *only the d==0 branch* appends `-1`, so the ring reads
   `[pending..., seq, val, marker]` and the entry sighting disappears. The relap path re-sends the
   marker and sets `BP = marker` (negative), which doubles as "clear the flag" — `d`/`a` only test
   `BP > 0`, so a negative backpack is a zero flag and costs no cell.

### What is left, measured

`in-order` is 768 ticks / 6 rounds = **128 per round**, of which the man walks ~90 cells. The other
~38 is **ring latency**: after the match the man relaps in 6 cells but the marker needs 34 to come
around, so the final "is there anything else?" lap is almost pure stall. Every case now costs
128-143 ticks per round regardless of how many pairs are buffered — the scan is no longer the cost,
the fixed round path and the ring circumference are.

Two ways out, both costed but not built:

- **Skip the empty lap with `q`.** `q` sets BP to the number of values in the nearest incoming pipe,
  and with a settled ring every buffered token piles up at the front of the ringback pipe, so
  `q` at a `c >= 10` cell reads the pending-token count exactly. If MAIN emitted a `d == 0` packet
  *directly* (as v1 did) and then used `q` to decide whether a drain lap is needed at all, the whole
  in-order case would never touch the ring: ~35 ticks a round instead of 128. The trap is that a
  token re-sent within the last ~9 ticks is still in the outgoing leg and uncounted, so the `q`
  must sit at least that far after the last `s` — fine after MAIN, racy on the marker path.
- **Pack `(seq,val)` into one token** — `tok = (seq+1)*1024 - val`, `B = (want+1)*1024`. Then
  `A = tok - B` is `> 0` for a future packet, and on the negative branch a single `+` recovers
  `tok`, whose sign separates MATCH (`> 0`) from a `-1` loss token (`< 0`). Ring capacity drops to
  16 tokens, so the ring is ~17 cells and the latency halves; the loop body is `r - X + s`, five
  cells. It is blocked on registers exactly like [[One persistent register per room]] predicts:
  the packing multiply needs a free `B`, so it has to happen in a second room, which then also has
  to be told when `want` advances (route HEAD's emitted values through it — it forwards to OUTPUT
  and does `B += 1` on the way). That second room also makes the marker unnecessary, because a
  HEAD that never exits its lap never needs to know where the lap ends.

### What changed

MAIN now branches on `d` **before** touching the ring, and only the `d > 0` arm pushes anything:

- `> r(seq) - b d` — five cells. `d>0` turns south into the INSERT lane, `d==0` walks straight on.
- `d == 0`: `r(val)` (still at `c<=8`, the input band) then east to `s(val)` at `c>=14`, the output
  band. `1` then `< W + M` on the way back sets `B = want+1`. Then **`q`** reads the ringback
  pipe's token count and `a` branches: `q == 0` -> straight back to MAIN, ~28 cells, no ring
  traffic at all. `q > 0` -> `N b s` pushes a **negative marker** (`-(want+1)`, so the sign test
  still works and `b` clears the drained flag for free) and drops into the unchanged drain loop.
- `d > 0`: the loss test `]]]]` + `a` moved onto the insert lane, so the hot path no longer pays
  for it. `+` recovers `seq`, `s`, `r(val)`, `s`, home.

The whole in-order case now never puts a token in the ring.

> [!warning] The `q` window
> `q` counts every value **in the ringback pipe** (`machine.py:350` sums all slots, not just the
> destination cell). A token that HEAD sent less than ~9 ticks ago is still in the ringout leg or
> in TAIL's hand and is **not counted**. If `q` under-reads, we skip a drain that was due, or push
> the marker *in front of* a token still in flight — [[Sends append behind the marker]] again.
> In v7 every path puts **>= 31 ticks** between the last ring `s` and the `q`, measured cell by
> cell: insert lane `s(val)` at (6,6) -> `q` at (3,10) is 31 cells, and the lap-exit path is
> longer still. That 31 vs 9 is the correctness margin, and any re-layout must preserve it.

Max ring occupancy dropped from 33 tokens to 31 (15 pending pairs + marker), because the arriving
packet is no longer pushed on the drain round.

## Lever B (pack `(seq,val)` into one token) — costed against a measurement, and it is a wash

Measured first, built never. Rebuilt v7 with the ringback pipe cut from 32 cells to 16 and ran the
cases that still fit in the shorter ring:

| case | ring 32 | ring 16 |
| --- | --- | --- |
| in-order | 156 | 156 |
| max-displacement swap | 1 241 | **986** |

So **halving the ring circumference buys ~20% on a lap-heavy case and nothing on a lap-free one**.
That is the entire latency half of lever B. The other half is loop work: the pair loop is 10 cells
but runs at **12 ticks/pair** because TAIL is a 6-cell shuttle and therefore caps the ring at one
token per 6 ticks; a packed loop is `> r - X` / `< + s ^` — an 8-cell rectangle, 8 ticks/pair.
Put together, lever B is **~1.4x**: 833 K -> ~595 K. It does *not* change our rank, because the
next rung up is `RGBTeam` at 505 172 (1.65x away) and the leader `Heuristic Artis` at 443 724
(1.88x). Full-pass standings at 2026-07-25T09:20+03:00: 443 724 / 505 172 / **833 000 (us)** /
858 600 / 905 719 — 46 of 48 teams pass all cases.

### And it needs a second room, which is not free

`B` is fully occupied by the comparison base, so the `*`/`{` that builds the token has nowhere to
live. Two placements, both costed:

- **A FRONT room that owns the input** (reads `seq,val`, holds `B = want` for the loss test, packs,
  forwards HEAD's drained values to OUTPUT doing `B += 1`). Clean registers, but it inserts a room
  into the **round-gated critical path** — the judge withholds round N+1's input until round N's
  output is emitted ([[Public and private test cases]], `judge.py:6`), so every round pays the
  extra room's latency twice. ~+20 ticks x every round wipes out the 1.4x. **Rejected.**
- **TAIL does the packing.** HEAD sends `-seq` then `val` (on the insert path `seq >= want+1 >= 1`,
  so `-seq <= -1` is a safe tag; the marker becomes `0` so it still forwards), and TAIL's forward
  loop branches on `X`: `A>0` token -> 6-cell shuttle, `A==0` marker -> 8, `A<0` -> a ~16-cell pack
  lane `N M 1 + M `10` W { M r N +` -> `s`. Off the critical path, but the pack lane grows TAIL by
  about as many cells as the shorter ring frees, so the footprint stays 400.

### Why sorting the ring is *no longer* a lever

Recorded so nobody re-derives it: pre-lever-A the note above estimated sorting at ~1.9x. With
lever A that is **wrong**. Laps per case are now `inserts + drain-rounds` if sorted, versus
`values drained` if unsorted — and lever A made an unsorted insert cost **zero** laps. For
block-reversed n=32 that is 32 laps either way; for drain burst sorting is *worse* (16 vs 15).

## Lever B re-costed against a per-cell measurement — it is a wash, and the reason above is wrong

### The measurement

`py/tcp_count.py` runs the 6 public cases through `littleman.judge.run_case` with a tracer
that counts executions per cell, so loop iterations, laps and rounds are counted directly rather
than inferred. Cells counted in v11: `(7,8)` = drain-loop entry (one visit per *pair* scanned),
`(7,12)` = MATCH, `(6,11)` = marker sighting (one per lap), `(1,4)` = `r(seq)` (one per round).

| case | ticks | rounds | laps | pairs scanned | matches |
| --- | --- | --- | --- | --- | --- |
| in-order | 135 | 6 | 0 | 0 | 0 |
| max-displacement swap | 1 117 | 17 | 17 | 31 | 1 |
| drain burst | 1 977 | 16 | 28 | 134 | 16 |
| loss | 454 | 16 | 0 | 0 | 0 |
| shortest | 15 | 1 | 0 | 0 | 0 |
| block-reversed n=32 | 4 026 | 32 | 59 | 270 | 32 |

Fits `ticks ≈ rounds×28 + pairs×10 + laps×(7..19)` to within 5% on every case
(88×28 = 2 464, 435×10 = 4 350, residual ≈ 950, total 7 764 vs measured 7 724).

### What that says

1. **TAIL is not the bottleneck, so the "12 ticks per pair" premise is false.** Between rounds the
   ring settles with every live token piled in the *ringback* pipe at HEAD's end. The drain loop
   therefore reads from a queue that is already full and never waits on TAIL's 6-tick shuttle; the
   measured cost is HEAD's own 10-cell loop, ~10 ticks per pair. TAIL only caps throughput when the
   ring is being refilled, which is off the critical path.
2. **Lap latency is the smaller half, not the larger.** Residual per lap is 19 ticks on `swap`
   (1.8 pairs/lap, transit exposed) but only ~7 on `drain burst` and `block-reversed`
   (4.6 pairs/lap, transit hidden behind the pair reads). This is consistent with the earlier
   ring-32→16 experiment (`swap` 1 241 → 986, i.e. −15/lap) — that experiment only ever measured
   the one case where transit is *not* hidden, which is why it over-generalised.
3. **So packing buys 10 → 8 ticks per pair and roughly halves the residual.** 435×2 = 870 ticks plus
   ~475 of residual = **−1 345 total, −224 on the mean**: 1 287 → ~1 063, i.e. **1.21x, not 1.4x**,
   and that is *before* paying for the multiply.

### And the multiply cannot be paid for

Worked through in full; recording the dead ends so nobody re-derives them.

The encoding is right: `tok = (seq+1)*1024 - val`, `B = base = (want+1)*1024`, `A = tok - B` is
`> 0` future / `= -val` match / `= 0` if the marker is set to `base` itself — a **three-way split in
one `X`**, and MATCH gets `val` for free as `N`. Loop is `> r - X` / `^ s + <`, 8 cells. The marker
is refreshed on relap by `b + s` (A is already 0 at the marker, so `b` clears the drained flag for
free). That part is clean and worth keeping.

What kills it is [[One persistent register per room]] applied twice:

- **HEAD cannot hold both `want` and `base`.** MAIN needs `d = seq - want` for the drain/insert
  branch *and* for the `]]]]` loss test; the loop needs `base`. `base = (want+1)*1024` and HEAD has
  no way to scale (`{`/`}` need `B = 10`, `*`//` need `B = 1024`, and `B` is the thing being
  scaled).
- **Deriving `d` in the scaled domain costs more than it saves.** With only `base`, MAIN can get
  `d*1024` (ask a MUL room for `S = (seq+1)*1024`, then `-`). The branch is then a free `X`, but the
  loss test becomes `d*1024 >= 16384`, i.e. `b` + **14** `]` + `a` — 16 cells, a whole HEAD row.
  No power-of-two threshold separates legal `d ≤ 15` (`D ≤ 15 359`) from loss `d ≥ 16`
  (`D ≥ 15 385`); `D+1024` then `]`×14 works but `+1024` needs the constant, which needs `B`.
- **A helper room cannot hold the constant and `want` at once either.** A MUL room with `B = 1024`
  computes `S = seq*1024 + 1024` in `* +` *without destroying B* — that much is elegant — but the
  moment it must also hold `want` (for `d`, or for the loss test) or park the product while reading
  `val`, `B` is gone and it needs a 6-cell `` `1024` `` literal to restore.
- **A PARK room (park `base`, multiply freely, read it back) works and hides its latency**, but the
  resulting insert lane is ~24 cells against v11's ~10.
- **A front room that owns the input is the only clean split, and it sits in the round gate.**
  Costed at ~12 ticks/round minimum for the seq→S round trip = +1 056 ticks over the 88 rounds =
  **+176 on the mean** — which is 80% of the 224 the packing wins.

Net at unchanged footprint: **−224 + 176 ≈ −48 ticks on the mean, ~1.04x**, and it needs a 4th
functional room and a 5th and 6th pipe on HEAD, which does not fit in 18x18 (bottom band is already
INPUT 3 + TAIL 6 + OUTPUT 3 + hairpin). At 19x19 it is a net **loss**.

> [!warning] Retired: [[#Lever B (pack `(seq,val)` into one token) — costed against a measurement, and it is a wash|lever B]]
> Twice costed, twice a wash, now for a *measured* reason rather than an estimated one. Do not
> rebuild it unless someone first finds a way to give HEAD both `want` and `base`.

### Ideas that died with it, and why

- **Counted laps (drop the marker; `q` gives the live count, `]` halves it to pairs, `m` counts
  down).** This removes the marker's ring transit entirely and is the single best idea in this
  session — but it needs **two** counters: one for the countdown and one for "did this pass drain
  anything", and BP is the only one there is. Every encoding tried (extra `m` on match, skipping the
  `m` on match, resetting to a constant 15) either exits early and skips tokens, or blocks reading a
  token that no longer exists. Revisit only if a second flag can be found.
- **Two parallel rings (seq ring + val ring, one shared TAIL with `U`).** Halves each ring to 16
  tokens, so transit ~22 instead of ~37, with no arithmetic and no critical-path cost. Worth ~1.1x
  on the measured model — but it needs **4 ring pipes** on HEAD (6 total) and `r(ringback1)` /
  `r(ringback2)` / `r(input)` all distinguishable, against a v11 margin that is already 1.
- **`gap = minseq - want` cached in BP to skip laps that cannot match.** Correct and cheap to
  *decrement*, but `min(gap, d)` on insert needs an A-vs-BP comparison that does not exist. The safe
  degenerate version (`gap := 0` on every insert) buys 1.86x on `swap` and nothing anywhere else —
  **1.07x overall**, because laps concentrate in the *relaps* of the two big reversed cases, not in
  one-lap-per-round cases.
- **Pushing the marker earlier in the round** so its transit overlaps MAIN's work: the zigzag is
  forced (`r(seq)` and `r(val)` want low `c` for the input band, `q` wants `c >= 9` for ringback,
  `s(out)` wants `c >= 13`), so the push moves from cell 22 to cell 17 at best. ~7 ticks/lap.
- **A shorter ring.** Capacity `2*15 + 1 = 31` tokens is a correctness floor and transit is one
  tick per cell, so there is no layout that shortens transit without shortening capacity.

pipe for `want mod 16` and execute a blocking `r`; out-of-order inserts do not wake it. After a value
arrives it broadcasts with `S`, increments `B = want`, walks to the next fan row, and blocks again.
The 16 rows form a cyclic snake. This is stronger than H2's proposed polling reader: there is no
`q`, branch, or per-round reader wake-up.

Implemented as `rooms/tcp-fan-reader/base.room`, generated and binding-audited by
`py/tcp_fan_reader_gen.py`. Every slot `r` is on the corresponding west-wall fan row (minimum
nearest-pipe margin 1); every `S` intentionally broadcasts to `output` and `feedback`. The wrap
riser is a separate column — the first version reused the odd-row turn column and step-capped, a
machine-level falsifier caught by the probe.

`programs/tcp/fan-reader-probe.eman.toml` connects a 16-output source, the reader, output, and a
feedback sink. All 18 pipes declare `min = 2, max = 40`; this probe needs two values of capacity per
slot, while the ceiling prevents a meaningless arbitrarily long fan. Results using `lmp`/`lmr`
semantics only:

- `lmp ... --logic-check --json`: **1/1**, 32 outputs (two complete fan cycles), **302 ticks** =
  9.44 ticks/value.
- `lmp ... --check --json`: **1/1**, seed max-dim 31, 244 occupied interior cells, area floor
  about 16x16, 85 routed pipe cells, 308 ticks.
- `lmp ... --seconds 20 --keep 3 --json`: best **25x25**, 303 ticks; alternatives 26x26/302 and
  27x27/305. The reader itself is 11x20 and the source 8x20, so 20 is the room floor; 25 versus
  area floor 16 is an arrangement/control-room problem, not a reader-room problem.

The reader subhypothesis is **confirmed** and clears the tick gate by a wide margin. The full H2
score claim remains unverified.

### H2 experiment 2 — direct feedback races; event guard is required

A first full netlist used `S` to broadcast each drained value to output and back to a writer holding
`B = want`. It exposed two falsifiers under `--logic-check`:

1. Using `R` for packet input is unsafe: a feedback token that arrives after `q` samples can be
   consumed as the next `seq`, causing an immediate false loss. Binding packet reads explicitly to
   input fixed this.
2. Giving feedback capacity 16/17 avoids burst deadlock but does **not** make it timely. The writer
   can sample `q` before the final feedback values arrive, then block on the next packet; when the
   judge releases that packet after the burst output, `want` is stale. Five public cases passed, but
   `block-reversed n=32` emitted `-1` at round 32 instead of value 190. Pipe capacity and event
   ordering are separate constraints.

The corrected topology removes `want` from the writer. `rooms/tcp-fan-writer/base.room` now sends a
negative sequence event to a future GUARD and Y-splits a value-carrying absolute-slot address worker;
`py/tcp_fan_writer_gen.py --audit` records all bindings. READER sends positive drain events. A guard
can process both with `R`: positive means `want++`, non-positive means check `seq-want`, provided the
netlist constrains the writer-to-guard event behind reader-to-guard feedback. This avoids the stale
register entirely, but the guard room was not completed in this session, so the broken full netlist
was removed rather than left as a candidate.

H2 is therefore **revised, not rejected**: the key 9.44-tick/value reader works, and the remaining
blocker is a small ordered-event guard plus concrete packing, not fan semantics. No tcp candidate
passed public+fuzz end to end, so nothing was submitted.

### Hypothesis H3 — split the pair loop into concurrent sequence and value lineages

### Hypothesis H4 — `U` can make the pair scan an eight-cell cycle

#hypothesis #refuted. `U` combines a receive with a turn away from the incoming ringback pipe, so it
looked like a possible replacement for one of v11's two plain direction cells. **Price and
falsifier:** the only useful result would be an 8-tick settled miss cycle (saving 2 × 435 public pair

The smallest experiment is the already isolated v11 miss cycle, audited instruction by instruction
against the language reference. A miss must execute, in order, `r(seq), -, X, +, s(seq), r(val),
s(val)`: seven state/pipe operations. The value is positive, so the existing second `X` is also a
working corner. A closed orthogonal grid walk needs four turns and has even length. `U` can combine
`r(val)` with the one remaining plain corner only *after* `s(seq)`; this changes the nine-cell walk
(`7` operations plus the two other turns) back to the next possible even cycle, **10 cells**. Using
`U` for `seq` has the same count. Using it before `s(seq)` overwrites A with `val` and reverses the
pair unless B or BP parks `seq`; B permanently holds `want` and BP holds the drained flag. Thus the
proposed 8-cycle is below the instruction/turn lower bound, and v11's measured 10 ticks is tight.
No larger integration was warranted. This is the same falsifier H3 reached experimentally from the
split side, now covering the only remaining receive-and-turn opcode.
