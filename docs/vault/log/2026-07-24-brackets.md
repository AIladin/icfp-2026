# brackets — log

Read a length-prefixed ASCII string of `( ) [ ] { }`; print `0` if balanced, else the 1-based
position of the first offending closer, or `n+1` if openers are left unclosed. `n ≤ 64`, depth ≤ 32.
Scoring is [[Scoring model|footprint-tick]]; server runs **26** cases even though `privateTestCount`
reads 0.

## Design

Two work rooms, forced by [[One persistent register per room]]:

- **Room C** — `B` = the stack, `BP` = scratch bit-decoder, `A` = working.
  The stack is a base-4 number with digits `{1,2,3}` = the bracket type, so *empty* is exactly `0`
  and a pop from empty can never fake a match (digit range 3 < base 4). See
  [[Bracket stack in one register]].
  - push: `A=t`, `++++`, `M` → `S = 4S + t`
  - pop:  `W - M 4 W / W N X` → `X` sees `-(S−t mod 4)`; `0` is a match and the quotient in `B` is
    already the new stack.
  - classification is a `b`/`x`/`]` tree on BP — [[Decoding a byte with the backpack]] — because
    `B` is taken by the stack, so no constant can be loaded.
  - end of input via `q`+`d` on the input pipe (no room for a countdown).
- **Room P** — `B` = the 1-based position `i`, owns the output pipe.
  C pings it once per character with `A = c` (always > 0), so P's dispatch is `b`,`a`:
  `>0` increments, `0` = "emit i", `-1` = "emit 0".

## The floor arithmetic

Worth writing down, because it says the gap is structural (see
[[Brackets floor is a two-room tick floor]]):

- local mean is 10.2 characters per case, server ≈ 20; local ticks read ~1.7x optimistic vs server.
- current cycle ≈ 50 ticks/char, of which **~30 is pure travel** — the leaves fan out east to
  column 19-22 and the shared lanes walk all the way back west, then 12 rows north to the head.
- an irreducible cycle for this design is `q d r s b x` + 1-6 `]`/`x` + 4-9 chain cells ≈ 20
  instructions, so ~20-25 ticks/char once travel is squeezed out.
- to reach 9,990 the leader must be running roughly **4-8 ticks per character in an 8×8-10×10
  grid**. That is below the cost of a single classification tree, so they are not doing
  read-classify-update per token the way we are.

The [[Bracket stack in one register#The ceiling|int64 hole]] is closed: digits `{1,2,3}` in
**base 3**, so push is `+++M` and the divisor is `3`. Bijective base 3 makes `}` on an empty stack
a false match (`-3` *is* divisible by 3), so the pop lane opens with `W X` — `S == 0` goes straight
west into a two-cell handler where `A` is already 0, `S > 0` turns north onto the arithmetic row.
That costs 2 cells and is a **wash on ticks**, because base 3 also deleted a `+` from every push.
Confirmed by 288 adversarial depth-32 cases (`scratchpad/brackets/deep.py`) that the base-4 program
fails and this one passes.

The 1.34x came entirely from shrinking the loop's bounding box, which is the right frame: the
per-character cycle is a **closed circuit, so it costs at least the perimeter of the box it spans**.
Three edits, no semantic change:

- pop entry columns moved from 19/20/22 to 17/18/19 by giving `)` — the commonest closer, and the
  one that walks furthest east along row 2 — the nearest entry, and letting `[` turn west over the
  opener subtree's own `]`s instead of claiming a column of its own.
- the `}` leaf's `v` deleted: `bit5 = 1` already leaves it heading south, so the turn cell was pure
  height. That one character took the grid from 23 to 22 rows.
- the opener subtree moved from row 8 to row 5 and both lanes up with it, so the return leg up
  column 1 is 5 rows instead of 9 and `(`'s descent is 4 cells instead of 7.

Width 22 is now structural: the closer subtree needs `> ] ] ] x` out to column 17 (`]` and `}`
differ only in bit 5), the three pop entries must sit east of the arithmetic row, and column 16 is
spoken for by `{`. Cutting a column needs a different tree, not a different packing.

## The real lever nobody has pulled: pipeline it across rooms

**Rooms run concurrently, so per-character cost is `max` over rooms, not the sum.** Our two-room
split does not exploit this at all — room C does ~45 of the ~46 ticks and room P idles. Splitting
the *classification* away from the *stack* would make both loops short and overlap them:

- **Room D** — `B` pinned to **5** forever (`5 M` once in the prologue, and nothing else ever writes
  `B`). Then `r` `b` `}` yields `A = c >> 5 = 1,2,3` — the bracket *type*, in one instruction, with
  no `]` walk and no eastward fan. Two `x` tests on BP (bit 0, then bit 1) split opener/closer;
  closers `N`. Send `±t` on. Whole loop ≈ 9 instructions.
- **Room S** — `B` = the stack. `r` `X` is the entire dispatch: `>0` push, `<0` pop, `0` end of
  input. Push is `s +++M`, pop is `N s W X - M 3 W / W N X`. No `q`, no `d`, no BP at all.
- **Room P** — unchanged; S forwards a positive ping per character so the ordering stays single-file
  (P must not have two incoming pipes, or a verdict can overtake the pings that set `i`).

That is ~16 ticks in D against ~18 in S, so ~18 ticks/character against our 45. I did not build it:
the layout is the whole job, and every attempt collided on the same constraint — `d`/`a`'s
straight-through path is the end-of-input handler, and it sits exactly where the leaves want to
return. The fix is a **`v` junction cell on the return row**: leaves arriving from either side land
on one `v`, which drops into a short vertical `q`/`a` head, so the head no longer has to be
approached from one particular side.

Also ruled out, so nobody re-derives it: **there is no branch-free decode.** Exhaustive search over
every 1- and 2-operation form `f(c)` with pinned or reloaded constants in `-300..300`
(`scratchpad/brackets/search.py`, `search2.py`) found nothing mapping the six codes to `±{k,k+1,k+2}`.
The sign has to alternate against `c` non-monotonically and no single `%`, `&`, `~` or shift does
that. Classification is mandatory; the only question is which room pays for it, and the answer is
the room whose `B` is free.

## Known hole (fixed 2026-07-25, see above)

Depth-32 stacks whose *bottom* bracket is `[` or `{` overflow int64: 32 base-4 digits of value 3
is `4^32 − 1 = 2^64 − 1`, which reads as `−1`. Found by fuzzing (`scratchpad/brackets/fuzz.py`,
134 cases, this is the only failure). The server's 26 cases do not hit it. The fix is bijective
base 3 (digits `{1,2,3}`, base 3, sentinel `S₀ = 1`), which caps at `3·(3³³−1)/2 ≈ 8.3e15` and also
shortens the push to `+++M` — but it needs one extra `quot == 0` test on the pop path, because
`)` on an empty stack is then a false match.

### What actually paid

- **`X` reads the sign of A, so one instruction is a three-way branch.** Room P used to do
  `b` then `d` then `x` to tell "+1 / emit i / emit 0" apart. `r X` does the whole split: `A > 0`
  turns clockwise, `A == 0` goes straight, `A < 0` turns counter-clockwise. That deleted two cells,
  a row and a column, and turned room P from 5 interior rows into 3. Written up as
  [[X on the sign is a free three-way branch]].
- **Stack `q` and `d` inside the return column.** The head used to be a horizontal `> q d` costing
  two columns of its own. Put `q` and `d` *in* the climb column, one above the other, and the
  returning man walks them on his way up — `d` then turns him straight onto the read row. Two
  columns freed, two ticks saved, no cells added.
- **A `v` in front of an `x` is a two-tick direction flip** ([[Bounce off an arrow to flip an x]]). `x` turns by the backpack's low bit
  *relative to the direction of entry*, so bouncing a man off a `v` back into the same `x` sends
  him the other way. That turned `)`'s 13-tick excursion (five columns east, five rows south to
  reach the far drop column) into a drop right beside the funnel: `)` went 50 → 40 ticks and the
  whole east column emptied out.
- **`]` cells are free to walk over once classification is done.** The backpack is dead after the
  last `x`, so a leaf can descend straight through another branch's shift chain. That is what made
  the short `)` drop column legal at all.

### What did not pay — measured, not guessed

Every attempt to shorten the loop by moving one piece was **exactly cancelled** by the piece it
displaced. The ring's perimeter, not its contents, is the cost:

- moving the pop chain west shortens its tail into the climb by exactly what it adds to the funnel
  run on the row below;
- shifting the whole tree two columns west closes the two-cell gap on the read row and opens an
  identical gap between the branch point and the drop column, which cannot move west past the
  funnel;
- putting `+++M` in the return column instead of the lane relabels four travel ticks as four work
  ticks and saves nothing, because both legs are walked either way. **Making the return leg do
  work only pays when it lets you delete cells, not when it merely relocates them.**

Per-branch ticks at 19×19: `(` 22, `{` 36, `[` 40, `)` 40, `}` 44, `]` 48; instruction counts are
11-20, so **~55% of every character is travel**. Closing that needs a global re-layout, not local
moves — the west edge (rows 15-17, columns 1-7) is already packed solid.

### Next lever, for whoever picks this up

`]` is now the worst branch at 48 ticks: it is deepest in the tree *and* pays a detour, because the
opener sub-tree's digits at columns 14/15 block the only nearer drop columns. Freeing those is worth
~6 ticks/char.

Beyond that the remaining 2x is the pipelined three-room split already described above — but note
the arithmetic has changed. It only wins if all five rooms fit in **≤24×24**: at ~18 ticks/char the
server would read ~380 ticks, so 576 × 380 ≈ 219k against today's 275,860, and 676 (26×26) ≈ 257k is
barely worth the risk. Two work rooms plus I/O in 19×19 is a genuinely hard baseline to beat.

## 2026-07-25 lightning endgame — 275,860 → 232,408 (1.19x)

Two submissions, both verified 26/26 by `icfp submit --wait`.

### What paid

- **The ring costs its perimeter, so pull every subtree as far WEST as the funnel
  allows.** The old grid had two blank cells on the read row before the bit1 test and
  a blank west of the arithmetic `X`; closing both moved the whole classification
  tree two columns west and the drop columns with it. Both legs of the loop shorten,
  so it is 4 ticks for every character that is not `(`. 870 → 721 server ticks.
- **The prologue does not need a row of its own.** `@ v` drops down the return
  column and swallows `n` *inside* it (`r` sits in the drop column, not on a row of
  its own), and the end-of-input handler moved onto the rows the tree already
  occupies. That deleted a whole row.
- **End-of-input is once per case, so spend cells, not ticks — but spend them
  INWARD.** The two tails used to hang off the east edge in their own two columns.
  Dropping the `S>0` tail down a live column of the tree (it threads two `]`, which
  are harmless because BP is 0 there) and running its tail west along an empty row
  freed both columns: 19 wide → 17. `(`'s digit moved one row up its own drop column
  to open that row.
- **`room()` must be sized, not just compressed.** Room C's right wall was inheriting
  its column from the *output room* two blocks away, so freeing interior columns did
  nothing until the rectangle itself was narrowed. 361 → 324 in one edit.

### What did not pay — measured again

Every further relocation is exactly cancelled, confirming the earlier finding. The
drop columns are pinned east of the funnel `W`, the arithmetic row cannot start west
of the climb, and the opener digit row cannot merge with the push lane. Shifting the
read row one more column west moves the collision, it does not remove it.

### Where the floor is now

`18 x 18` is structural for this topology: height is `room P (5) + pipe (2) + room C
(11)` and a pipe cannot be shorter than 2 cells; width is `room I (3) + room P (10) +
pipe (2) + room O (3)`. Room C itself is only 17 x 11. Beating 324 needs either room C
at 10 rows or room P at 9 columns — both are packing problems, not logic problems.

### Economics — the estimate in "the real lever" section above is stale

That section was written against a 361-footprint baseline and concluded "wins if it fits

Best case for the split is `max(D_cycle, S_cycle)`; hand-counting the layouts below gives
D = 12/18/20 ticks for opener/`(`/closer and S = 12 (push) / ~20 (pop), so **~18-20 local

| --- | --- | --- |
| 24x24 = 576 | 132k | **loss** |
| 22x22 = 484 | 111k | 1.09x — not worth the risk |
| 20x20 = 400 | 92k | 1.32x |

Three work rooms plus I/O in **20x20 or smaller** is the whole ask, and today's two-room
program needs 18x18 for *two* rooms. That is the reason to stop, not the logic.

### The logic, which is now completely solved — build it from here

Three rooms, `D` (decode) → `S` (stack) → `P` (position, unchanged). Single-file: only S
talks to P, so P keeps one incoming pipe and no verdict can overtake a ping.

**Room D — `B` pinned to 5.** `c >> 5` is `1,2,3` for `()`, `[]`, `{}` in one instruction,
so the six-leaf tree collapses to two `x` tests. Opener/closer: `c` bit0 = 0 is `(`;
otherwise bit1 = 1 is an opener. Interior 6 rows x 7 cols, every `x` entered heading south:

```
r0:  >  0  s  H                       <- end of input: send 0, halt
r1:  d  r  b  }  v                    <- read row; d turns east while q > 0
r2:  q  .  v  ]  x  s  v              <- x = bit0; '(' goes east and drops at c6
r3:  ^  s  x  N  s  v                 <- x = bit1; opener west, closer east
r4:  ^  <  <  <  <  <  <              <- shared return row
r5:  @  5  M  r  ^                    <- prologue: B=5, swallow n, join the return row
```

Three things that were not obvious:

- **The prologue has no home unless it gets its own row.** `d`'s straight-through
  (end-of-input) path owns `r0` and every leaf wants `r4`; every attempt to fold `5 M r`
  into either row collided. Row `r5` entering the return row at `c4` is the cheap fix —
  it is west of nothing and costs one row, not one column.
- **`}` may be placed anywhere after `b`**, because the `x` tests read BP, not A. It sits
  on the read row only because the man walks there anyway.
- `q`/`d` is still the only end-of-input test: `B` is the constant and BP is the decoder,
  so there is no register left for a countdown.

**Room S — `B` = the stack, and the pop test gets much cheaper.** Head is
`1 s r X`: the ping is at the *top* of the loop, so `i = k` while character `k` is being
processed **and** `i = n+1` at end of input — the unclosed-opener case then needs no bump
at all, it just sends `0`. `X` on the received value is the whole dispatch: `>0` push,
`<0` pop, `==0` end of input.

- push is `+ + + M` on `A = t, B = S` (gives `B = 3S + t`), 12 ticks round trip.
- pop no longer needs `W X ... W` to reject the empty stack. With `A = -t, B = S`, a
  single **`+` gives `A = S - t`, and `A < 0` is exactly "mismatch or empty stack"** —
  both of which emit `i`, so they share one handler. Proof: `S - t < 0` with `S > 0`
  forces `S < t <= 3`, so the top digit is `S != t`, a real mismatch.
- `A == 0` (exact match, stack empties) **needs no branch of its own**: feed it straight
  into the normal `N M 3 W / W X` lane and it produces quotient 0, remainder 0, i.e.
  `B = 0`. That deletes the special case entirely.
- so the pop lane is `+ X` then `N M 3 W / W X`, and `X` on the remainder (never negative,
  since `B = 3`) splits match/mismatch.

**What actually blocked the build: room S will not close.** The head `X` has three exits
and so does the pop `X`, and in a 5-6 row room one of the six always lands on the push
lane, the climb column, or the arithmetic row. Roughly a dozen arrangements were tried.
The two constraints that fight are:

1. the push lane must be `+++M` **plus** a turn cell, i.e. 5 cells in a straight run
   ending at the climb column — so the climb column's neighbour is always `M`; and
2. the head `X`'s *straight* exit (end of input) descends a column that the arithmetic
   row must cross, because the arithmetic row spans nearly the whole width.

The fix is almost certainly to spend cells, not ticks, on all three terminal handlers
(pop-mismatch, empty-stack, end-of-input) by routing them **out of the ring into a single
`0 s H` reached from a junction**, exactly the trick that took the two-room program from
19 to 17 columns. Three of the four terminal cases send the identical `0` — only
"balanced" differs (`1 N s H`).

### Also worth knowing

- **Room P cannot go below 3 interior rows.** Its `X` has three exits and in a 2-row room
  the straight exit is always a wall, whichever way the man enters. So height
  `5 + 2 + 11` cannot be attacked from the P side; only room C at 10 rows moves it.
- Reducing room P's width alone is worthless: room C is *also* 18 wide, so both bands are
  binding and `max(w,h)` does not move until width and height drop together.
- Re-checked the closer sub-tree for a cheaper bit than 5: `]` and `}` differ at bits 2, 4
  and 5, but `[` vs `{` differ **only** at bit 5, so the opener side forces the four-`]`
  walk regardless. No shift is saved by re-picking bits.
