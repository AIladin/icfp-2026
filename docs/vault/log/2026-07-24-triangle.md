First program written. `triangle` — output the *n*-th triangular number, `0 ≤ n ≤ 1000`.

## Attempt 1 — the backpack loop (wrong)

```
+-+   +--------+
|I|>->|@rbW>dsH|
+-+   |     +  |
      |     m  |
+-+   |    ^<  |
|O|<-<|        |
+-+   +--------+
```

`r b W` reads `n`, copies it to the backpack, then swaps so `A = 0` (accumulator) and `B = n`
(addend); `d` turns into an 8-cell cycle that does `A += B` and `m`.

**It computes `n²`, not `T(n)`** — nothing ever changes `B`, so it adds `n` to itself `n` times. It
passed the `zero` and `one` cases and nothing else, because `0` and `1` are the only fixed points of
`n² = n(n+1)/2`.

## The wrong conclusion I drew from it

I claimed a constant could never be routed into B while A was live, since every constant-loading
instruction writes A. **False** — [[Park and swap]] (`M` `<const>` `W`) does exactly that in three
ticks, using B itself as scratch. The user found it independently while fixing the program.

The *conclusion* about loops survives, for a narrower reason: in `sum += k; k -= 1` both hands are
live, so parking A destroys `k`. A decreasing-addend loop still needs a second room. Recorded in
[[Bounded loop with the backpack]].

## Attempt 2 — closed form, 13 cells (passes all public cases)

```
@1WrW+*M2W/sH
```

`1W` sets `B = 1`, `r` reads `n` (leaving B alone), `W` restores, `+` builds `n+1`, `*` gives
`n(n+1)`, then park-and-swap loads `2` and `/` halves it.

## Attempt 3 — 11 cells

`*` and `+` both leave B untouched, so `n` can stay parked in B across the whole polynomial — no
need to construct `n+1` at all, since `n(n+1) = n² + n`:

```
@ r M * + M 2 W / s H
```

Two cells and two ticks cheaper. Generalised in [[Single-variable closed form]].

## Layout — 9×9, footprint 81

The eleven cells are not what costs footprint; the two 3×3 I/O rooms and their pipes are. Mounting
both on the **top** makes them share one 5-row overhead and cost zero extra width:

```
+-+   +-+
|I|   |O|
+-+   +-+
 v     ^
 v     ^
+-------+
|@rM*+Mv|
| Hs/W2<|
+-------+
```

Alternatives measured: I/O stacked west 12×6 → 144; I top / O right 12×12 → 144; single interior row
13×5 → 169. Written up as [[I-O rooms belong on one side]].

Walk is `@ r M * + M v < 2 W / s H` — **13 ticks flat, independent of n**. Projected score
`81 × 13 ≈ 1053`, against roughly `256 × 1400 ≈ 360 000` for a correct version of the loop.

## 17:35 — 8×8, score 832, by disbelieving our own runner

The leaderboard's best was **832** against our 1053. `832 = 2⁶ × 13 × 19`, and its only square
divisors are 1, 4, 16, 64 — so the leader was at `8×8 × 13 ticks`, with **ticks already tied**. The
whole gap was one row and one column.

Solving the tick budget per interior shape showed only **6×2** reaches 13 ticks inside 8×8 — and it
holds exactly 10 instruction slots, which is exactly `@ r M * + M 2 W / s` with **no room for `H`**.
So the leading program had to end by walking into a wall.

Our runner said that was impossible, twice over. Both were runner bugs:

- [[Output survives the wall error]] — the run ended at the movement phase, losing a value still in
  the output pipe. The error is now armed at movement and thrown at the next execution phase, so
  phases 1–2 of that tick still run.
- [[Pipe start scanning may be greedy]] — every one of the 12 legal 8×8 geometries has a 2-cell pipe
  whose second cell backs onto a wall, and the loader read that as a second one-cell pipe. Candidate
  walking is now speculative: an error is only fatal if no other pipe claims the cell.

The server accepted `programs/triangle.man` and scored exactly **832**, confirming both. Regressions
added; the runner now reproduces the score locally.

```
+------+
|@rM*+v|
|s/W2M<|
+------+
+-+>^ v
|I|+-+<
+-+|O|
   +-+
```

**The transferable lesson**: when `lm` rejects a layout that should be legal, suspect the runner
first. A rival's score is a real oracle — you can factor it and work backwards to the shape of their
program.
