`memory` — simulate a 100-cell RAM. Input is a stream of `0 addr` (READ) and `1 addr value` (WRITE);
emit each READ's value in order. **Solved, 24/24 on the server**, submission
`5e776275-2859-4b51-9cdd-1ab4ee20e8f0`.

## The design argument

Started from the obvious pattern — one room per cell, broadcast the address, the matching cell
answers. The language actively supports it: `S` sends A into *every* outgoing pipe, `R` takes from
any incoming pipe with a value ready, so fan-out and fan-in are both one instruction.

It has one hard blocker, and chasing it produced the most reusable idea of the session:
[[One persistent register per room]]. `r` writes A, every binary op reads B, so B is the only
register surviving a message — and the cell wants it for its *value* while the match wants it for its
*name*. Way out: [[Name in the geometry]], where `b x ]` walks the address bits and the name becomes
the room's shape. Written up and drawn as [[Memory cell room]], which works (10-tick write, 18-tick
read) but is not what we shipped: 100 rooms will not compress below ~3000 cells, and footprint is
charged squared.

The opposite trade won — [[Delay line ring]], where pipes are the RAM and rooms are the ALU. **Pipes
store ~1 cell per value against a room's ~30.**

## The encoding argument

First cut used `-1` as the wrap marker. The user caught that `-1` is a legal *value*
(`-1000000 ≤ value ≤ 1000000`), so the design was only safe by the invariant "we never lose pair
phase". Settled it structurally instead: the scan always swallows one value token blindly after each
address token, so values are **never classified** and a stored `0` or `-1` cannot be read as the
marker. `X`'s third outcome does the rest — marker `0`, addresses stored as `-(addr+1)`, one tick to
tell them apart with no constant and no register ([[X is the only comparator]]).

Match test is `~` (XOR), not `-`: both address tokens are negative, XOR of two negatives clears the
sign bit, so the result is 0 on a match and **strictly positive** otherwise. That collapses `X` to
two outcomes and saves funnelling a second branch back into the loop.

## The build

`py/memory_gen.py` emits the grid. Two rules made ~35 position-sensitive instructions tractable:

1. **Every pipe on the south face**, so the row term of the Manhattan distance is identical for all
   four and only the column decides — I/O band cols 0–7, dead zone 8–9, ring band 10–17. Written up
   in [[Nearest pipe resolution]].
2. **One lane per row, each running one direction**, with column 0 as a north bus back to the top of
   the loop. A finished branch just runs west until it falls onto the bus.

The canvas raises on any cell written twice, which caught two overlapping lanes before a grid was
ever rendered.

## Three things that cost time

- **Undersizing the drum deadlocks, it does not fail.** A 34-token ring passed six cases and stalled
  on the seventh at exactly the point the ring filled: `s` blocks forever with no error, so it
  presents as a step-cap timeout at 5 000 000 ticks. The emitted prefix was *correct* and simply
  stopped, which is the only reason it was obvious.
- **A riser flush against a room wall is a second pipe.** Folding the drum put the vertical run in
  the column touching HEAD's east wall — every bend there has a room border behind it, so the loader
  legitimately read it as a pipe start. One column of clearance fixes it; see
  [[Pipe start scanning may be greedy]].
- **The first pipe cell must point away from the room**, so a pipe that wants to turn immediately
  needs one straight cell first. Bending on cell 1 puts the wrong cell behind the arrow.

### Where the ticks are

1313 ticks per operation, and the structure explains all of it: the ring holds `2k+1` tokens for `k`
distinct addresses (201 at worst), every operation walks a **full revolution**, and the scan cycle is
**16 ticks per (address, value) pair**. The full lap is not avoidable — the marker is the only
landmark that says "you have been all the way round", so an early exit on a hit still has to drain to
it. That leaves two real levers: **fewer tokens per entry** and **fewer ticks per token**.

### The measured ladder

| change | ticks/op | footprint | note |
| --- | --- | --- | --- |
| today | 1313 | 1225 | |
| tighten the scan cycle to 10 ticks/pair | ~820 | 1225 | pure relayout, see below |
| fixed slots: position *is* the address | ~660 | ~1000 | one token per address, no compare, no append |
| + [[Banked drums]] at `k ≈ 12` | ~120 | ~1225 | 9 addresses per bank |

The last row is the one that beats 31.8M, and it only works **because fixed slots make the bank head
tiny**. Today's head is 440 cells for ~35 instructions; a counting head needs no `~`, no query in B,
no marker arithmetic and no append path, so ~80 cells. Twelve of those plus their drums pack into
about the footprint we already have. Banking today's head would be 12 × 440 and lose.

### The 10-tick scan cycle

Sketched and verified on paper, not yet built. Flip address tokens from `-(addr+1)` to `+(addr+1)`
so `X` turns **clockwise** on an address, and the whole cycle becomes a 3×4 perimeter walked
clockwise, with both `X`s sitting on corners so their turns are free:

```
> r X     (10,1) corner, r, X: marker 0 -> straight east (exit); address >0 -> cw south
    s
    ~
^ r X     X: match 0 -> straight south (exit); miss >0 -> cw west
  s
```

Ten cells, seven of them instructions — `r s X ~ X r s` — against sixteen today. `~` still works
because XOR of two *positive* tokens is non-negative and zero only on equality.

## 19:40 — fixed slots: built, 7/7, and not an improvement on its own

Server score for the log-structured drum came back as **63.5M** (5th place, leader 31.8M). That also
calibrates the benchmark: 63.5M / 1225 = **51 836 average ticks** on the server, against 244 712 on
`memory_bench.py`. The bench is ~4.7x pessimistic, but it is the only local signal that moves in the
same direction as the server, so keep scoring against it.

Built the fixed-slot head (`memory_gen.build_slots`, `scratchpad/slots.man`): the drum holds exactly
100 values, **slot _i_ is address _i_**, and every operation shuttles exactly 100 tokens so the drum
ends where it started. That removes the comparison, the query in B, the wrap marker and the append
path in one go — the head counts instead of matching. **7/7 on the public cases, first run.**

Two tricks carried it:

- **The opcode rides in the sign of the counter.** `r` destroys A every iteration, so the opcode
  cannot live in a register — but B is untouched by `r`/`s`/`m`. Park `-(100-addr)` for READ and
  `+(100-addr)` for WRITE; at the target, `W` then [[X is the only comparator|`X`]] recovers both the
  branch and the count. Neither value can be zero, so the two branches are unambiguous. That is what
  lets READ and WRITE **share both loops** instead of duplicating them.
- **The loop test sits at a corner.** An 8-cell 2x4 rectangle whose top-left cell is `d`, entered
  heading north, gives `d`-first semantics for free: `addr = 0` does zero shuttles, and the turn
  costs nothing. Cells are `d`,`v`... wait — `>`,`d`,`r`,`s`,`<`,`^`,`m`,` ` — three instructions and
  five turns, **8 ticks per token**.

### It is not a win by itself

| synthetic case | log-structured | fixed slots |
| --- | --- | --- |
| 1000 tokens, **100 addresses** | 590 643 | **412 745** |
| 1000 tokens, **5 addresses** | **143 495** | 453 223 |
| bench score | **299 773 017** | 461 849 600 |

Fixed slots is **uniform cost** — always 100 slots per operation — so it wins where the drum is full
and loses where it is sparse. The log-structured drum is adaptive: `2k+1` tokens for `k` distinct
addresses. Since the bench mixes both, the total is worse and `programs/memory.man` stays as it is.

**This was still the right build.** Uniform cost is the precondition for every remaining lever, and
they all attack the same term — 8 ticks x 100 tokens:

1. **Wider shuttle cycle.** A 2-wide, `h`-tall loop has `2h` cells, 4 of them corners, so it can hold
   `n` `r`/`s` pairs plus one `m` when `2n+1 ≤ 2h-4`. Cost per token is `2h/n → 2 + 5/n`: **n = 10
   gives 2.6 ticks/token against 8, a 3x cut**, for 26 cells. Reaching a slot at 1-token granularity
   then needs a coarse pass and a fine pass — and `/` hands you both at once, since `A / n` leaves
   the quotient in A and **the remainder in B**. This also applies unchanged to the log-structured
   drum's 16-tick scan, so it is worth building either way.
2. **Banking** ([[Banked drums]]) is now much cheaper than the `k` x 440-cell estimate: with the
   loops shared and only the per-bank `r`/`s` duplicated, a bank costs ~25 cells, not ~440. A decode
   tree over `k = 16` plus 16 copies of loop1/target/loop2 is ~400 cells.

## 20:30 — the lap was the cost, not the cycle

Two server numbers came back and between them they say the whole story:

| program | footprint | bench score | **server** |
| --- | --- | --- | --- |
| log-structured, 16-tick scan | 1225 | 299.8M | **63.5M** |
| fixed slots | 1600 | 461.8M | **138M** |
| log-structured, 10-tick scan | 1296 | 267.3M | **55.2M** |
| same 16-tick head, hand-packed tighter (user) | — | — | **56.8M** |

Two things fall out. **The private cases lean sparse** — fixed slots pays 100 slots per operation
however few addresses are live, and it lost by 2x, so the adaptive `2k+1` drum is the right shape and
[[Banked drums]] is aimed at the wrong term. And **a hand-repack of the old head scored within 3% of
a rewritten scan loop**, which is the clearest possible statement that footprint and ticks were
contributing about equally.

### The 10-tick cycle, and why it only bought 1.15x

The scan cycle is now at its floor: a 2x5 perimeter with **both `X`s on corners**, so neither branch
costs a tick — a turn is what `X` does anyway.

```
>X      X1: marker 0 -> straight east; address >0 -> cw south, stay in the loop
rs      s pushes the address straight back; r picks up the value on the way round
s~      ~ compares against the query parked in B
r.
^X      X2: match 0 -> straight south (hit); miss >0 -> cw west, stay in the loop
```

Ten cells, seven of them instructions, against sixteen. Flipping address tokens to `+(addr+1)` is
what lets **both** `X`s use clockwise as "stay in the loop". The drain also stopped being separate
code: set `B = 0` after a hit (no address token can XOR to zero against it) and `BP = 2`, a third
opcode the miss path decodes with a second `m`/`a` test — same loop, ~30 fewer cells.

But it only moved 63.5M → 55.2M, because the old drain was already ~10 ticks/pair. The real average
was 13 ticks/pair, not 16. **The cycle was never the cost. The lap was.**

### Dropping the lap

The lap exists only because the marker has to be *found* to prove the whole ring was seen. A scan can
start anywhere if it can tell **first** time past the marker from **second** — so stop at the hit and
let the ring sit at whatever rotation that leaves.

Carry `BP = 2*op` and `m` once when the marker goes past:

| | before marker | after |
| --- | --- | --- |
| read | 0 | -1 |
| write | 2 | 1 |

`x` (low bit) splits **exactly** on marker-seen, because `-1 & 1 == 1` — the one place
[[Backpack instructions|`x`'s raw-bit reading]] of a negative backpack is the whole point. And `d`
still recovers the opcode either side of it: `{0,-1}` vs `{2,1}`. One counter, two questions, no
extra register.

Average scan becomes the **distance to the target**, ~`k/2` pairs, instead of a full `k`-pair lap —
and the drain disappears with it.

| | footprint | ceiling / sparse | bench score |
| --- | --- | --- | --- |
| 10-tick, full lap | 1296 | 492 540 / 72 663 | 267.3M |
| **10-tick, no lap** | **1156** | **344 651 / 72 663** | **160.8M** |

**1.66x**, and smaller too — the head lost two rows along with the drain. Submitted
`6ee19b30-8048-4ddd-b2bb-7860979c0727`, 24/24.

### Next

1. Footprint is back to being the binding term: 1156 = 34², and a sweep over every legal fold
   geometry cannot beat it because **height and width are now equal**. Cutting further means
   repacking the head itself (21x19 interior) or moving the fold underneath it rather than beside.
2. The remaining tick term is the ~40-tick per-operation overhead — setup, hit path, and the walk
   back to the loop entry — which now rivals the scan on sparse cases.

> [!warning] The bench overweights dense cases
> Dropping the lap was **1.66x on the bench** and only **1.10x on the server** (55.2 → 50.2), while a
> pure repack of the *old* head was **1.28x**. `memory_bench.py` leans on the 100-address ceiling
> case, and the private set evidently does not. Keep the bench for A/B on the same layout; do not
> trust its ratios across designs.

### What the repack was

Shipped in `build_tight`, `programs/memory.man`, 32x27 = **1024** against 1156:

- **I/O rooms belong directly under the head**, adjacent to each other, on 2-cell legs. They were 11
  rows below it, so both pipes were ~10 cells of pure bounding box. Same lesson as
  [[I-O rooms belong on one side]], one level further in.
- **RELAY straddles the ring-in column**, directly beneath the head. Its return pipe is then a
  *straight 2-cell riser* with no bend — and feeding RELAY from the **right** means nothing has to
  run back west at all, which is what the old layout was spending rows on.
- **An even boustrophedon row count** brings the fold back out on its own left edge, so the dedicated
  descent column disappears. Two columns of width for free.
- Freed of the westward lane, **the fold can run past the head** and down beside RELAY, so the rows
  the tighter layout cost were recovered.

Footprint is now bounded by **width** (32) with five rows of slack in height, so the next cut has to
come from the head's 23 columns, not the plumbing.

> [!warning] The ring has 12 cells of slack
> 213 cells against a 201-token worst case. [[Delay line ring|Undersizing deadlocks silently]] rather
> than failing, so the ceiling case in `memory_bench.py` is now load-bearing — run it before shaving
> anything off the fold.

## 2026-07-25 14:xx — where the ticks actually go, measured per cell

Submitted `9f33a3d4-e097-43fe-84b8-36a3e6bfb0e1`, **24/24, 24,144,432** = 576 (24x24) x 41,917
avgTicks. `programs/memory-24_1M-narrow-head-24x24.man`, generator `memory_gen.build_narrow`.
**The whole win was footprint** (676 -> 576); avgTicks got 5% *worse*.

### The profile (per-cell heatmap, `run_case(trace=...)`, public "interleaved cells" and k-sweeps)

`programs/memory_26_9M.man` is **not** the no-lap head — it is `SCAN_HEAD`, the **full-lap** one
(measured pairs scanned per operation ~= k, not k/2). The no-lap rewrite was never packed to 676.

Per operation, at k=5 / 200 ops: **95 ticks walking, 59 ticks scan cycle, 74 ticks blocked**.
The ~85 ticks/op the drum handoff called "per-op walking" is real and is column 0's north bus
(16 cells) + the top row (9) + full-width west lanes.

### But the walk is *hidden*, and that is the finding

Fitting ticks/op against k gives a **flat floor of ~220 ticks for every k <= 10** — that is not the
scan, it is the **ring pipe's 201-cell latency**. The model that fits every measurement is

> per-op = **max(ring cells, tokens x ~4.7)** + a small serial remainder

Proof: a head rebuilt 12 columns wide with the setup instructions moved onto the north bus, cutting
the walk 95 -> ~30, ties the champion tick-for-tick at every k (`build_scan_narrow`, same full-lap
logic, 625). **Cutting the walk buys nothing because the head is blocked waiting for the ring
anyway.** That also explains the drum: halving its ring moved 0.7% because its *serial* walk was
~175 ticks; it was never scan-bound or transit-bound, it was bound by its own head.

### Why no-lap lost on the server

A no-lap **miss costs 1.5 laps** (the marker must pass twice and the first pass starts at a random
rotation); full-lap costs exactly 1. Locally, cases with >50% misses run **1.2-1.4x slower** under
no-lap. The private set is miss-heavy — so `build_narrow` (no-lap) returned 41,917 avgTicks against
the champion's 39,779 despite scanning half as far on a hit. Break-even is ~50% misses.

### The one lever left

Ring cells and token count are the same number, and both are the binding term. **Halve them**:
one token per entry (`t = addr*2^21 + value + 1000001`), ring ~105 cells instead of 201. The
predicted per-op is `max(105, entries x 6) + ~20`, i.e. **1.6-1.8x at every k**, and the fold
shrinks with it. `py/memory_gen2.py` already builds a correct sorted packed drum (24/24 three
times) — it lost only on its 1444 footprint and its 175-tick serial head. **Port memory_gen2's
logic into the 12-column `SCAN_NARROW_HEAD` geometry.** Everything else has been measured out.

## 2026-07-25 20:10 — banked drum: built, verified, and worth 1.35x

`py/memory_gen3.py` cuts the ring into **two banks** (bank *j* holds the addresses with
`(addr+1) & 1 == j`). **7/7 public and 5/5 fuzz** (k = 1, 2, 8, 20, 40) under `--ephemeral-pipes`.
Handed over for packing as [[Banked drum handoff]]; design in
`programs/memory-banked2-handoff.man`.

### The profiler is the reusable part

`py/memory_prof.py` splits per-op cost into ring-wait and walk by counting ticks where a man is
`blocked`. That finally separated the two terms the whole problem turns on:

| champion | ticks/op | blocked/op | walk/op | |
| --- | --- | --- | --- | --- |
| k=5 | 137.6 | **165.9** | 59.1 | ring-latency bound |
| k=25 | 270.2 | 94.6 | **229.4** | scan bound |
| k=60 | 734.3 | 178.8 | **654.9** | scan bound |

So the champion is latency-bound when sparse and scan-bound when dense — and banking is the one
lever that hits *both*: half the pipe and half the tokens per bank.

### Measured

| | k=5 | k=25 |
| --- | --- | --- |
| champion (ring 213) | 137.6 | 270.2 |
| banked x2 | **99.1** | **175.7** |
| | 1.39x | 1.54x |

**Total ring capacity is unchanged** — 2 x 101 against 201 — so banking costs no pipe cells, only
duplicated code. The head splits at a column boundary: cols 0-7 shared (prologue, input reads,
output sends), cols 8-11 the bank block. A bank is therefore **4 columns, not a head**.

### Two things that would have been silent

- **`--audit` caught bank 1's sends landing on bank 0's ring.** At block pitch 4 the ring-out
  columns are exactly one block apart and a block's edge cells are equidistant from two banks'
  pipes. Pitch 5 fixes it; margins are still only one cell.
- **Banks must be stacked in row bands, not side by side.** Side by side, bank 1's arms have to
  cross bank 0's block to reach their own ring send, and the re-decode that needs cannot be done —
  on the write path A already holds the value just read from input.

### Why it stops here

1.35x on ticks at a comparable packed footprint is **~24.1M -> ~18M**, rank 16 to about 11. It does
not reach the 9.5M leader. **B=4 goes backwards**: the head widens 5 columns per bank against a
footprint charged squared, so width growth outruns the tick win. B=2 is the optimum.

The `Y` detour that led here is written up in
[[Examination points cost pipes, whatever the store is made of]]: storing values in little men
instead of a pipe cannot beat this, because a query reaches a man only through a pipe, so any
associative store costs `T >= N/P` for `P` pipes — and men cost *more* pipes per examination point
once injection spacing is accounted for.

**And that is where this technique stops being interesting.** `lm eval` puts us at rank 18 against a

Three orders of magnitude is not a packing gap or a tick gap, it is a different data structure:
somebody is not scanning a drum. Further work on the banked drum buys percent, not factors.

Two things learned along the way, both worth their own notes:
[[Rotating a room breaks its spawn]] (a man always starts heading east and rotation does not rotate

pair on the east wall so a drum can sit *beside* a head that is taller than it is wide.
