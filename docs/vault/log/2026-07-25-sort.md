## 01:20 — picking the algorithm

Opened `sort-numbers` off the back of `reverse-a-list` on the hypothesis that the 16-lane
[[Pipe fan stack|addressable fan]] carries over. It does not: `R` ties by pipe position, so the fan
is a fixed permutation, and sorting needs a value test. Priced the obvious alternative — a 16-wire
sorting network — and it dies on footprint: one room per comparator, ~60 of them, or 16 rooms + 30
pipes for an odd-even transposition array, ≥ 324 footprint for the array alone.

Pulled the public tests first instead of guessing:

```
warm up                  rounds=3 ns=[3, 4, 5]
already sorted           rounds=3 ns=[1, 5, 4]
all equal                rounds=2 ns=[4, 7]
reverse sorted           rounds=2 ns=[6, 2]
negatives and duplicates rounds=2 ns=[5, 8]
min to max size          rounds=3 ns=[1, 16, 2]
long case                rounds=4 ns=[16, 3, 12, 16]
```

`Σn²` averages 173 per test case — `O(n²)` is nearly free, so the whole score is footprint. Settled
on selection sort over a [[Delay line ring|ring]] with one comparator room. Written up in
[[Selection sort on a ring]].

## 02:00 — three bugs, all layout

1. **TAIL walked out of his own loop.** `@rv / ^s<` — `@` is not a direction cell, so the relay man
   ran off the top of the shuttle into the wall. Widened the room and parked `@` outside the cycle.
2. **Pipes that bend on their first cell.** `Canvas.pipe` writes the arrow for the *outgoing*
   direction, so a leg that turns immediately gets an arrow that does not point away from the source
   room — the loader then finds a different, shorter pipe somewhere else and the ring silently loses
   capacity. Every leg now starts with one straight cell. Same trap as the `memory` fold
   ([[Delay line ring]]).
3. **A riser crossing a corridor.** The round-done path rose through a column the new-min branch
   travels along, so a `^` intended for one man redirected the other. Cost a rebuild of the whole
   bottom half of HEAD.

7/7 on the first clean run, 529 footprint / 1752 ticks / **927,110**. Submitted
`c5576185-2b49-410b-8c02-a26bb2b5cdc8`.

## 02:50 — where the remaining ticks are

Profiled the `n = 16` round by hand against the measured 2240 ticks. The sort loop is at its floor
(8 cells, 8 ticks, both `X`es on corners the walk needs anyway). The cost is the **return bus**: the
marker handler and the new-min branch both leave the 8-cell cycle and walk ~9 cells back to its
single entry, ~55 times a round, ~500 ticks — 22%.

Cause is the pipe-column rule: the output `s` has to be far from the ring `s` for
[[Nearest pipe resolution]] to separate them, so the marker corridor bisects the room. Fix recorded
in [[Selection sort on a ring#Where the ticks actually go]] — put `COL_OUT` adjacent to `COL_RING`
so the boundary lands between them, and reorder the handler to `s(M) · r(C) · + · s(out) · - · s(C)`
so `-` rebuilds the parked bias token from `min - BIAS` after the emit. Not built yet.

## 03:30 — packing, pipelining, and the thing that actually worked

Chased "make one lap do more work", from [[Sorted packed drum]]. Two dead ends and one win.

**Packed tokens are register-dead.** `k` values in one word needs four things live — the running
minimum, the packed token, the extracted field, the radix constant — against **two** readable
registers. `BP` does not count: `b`/`m`/`]`/`q` write it and nothing reads it back into a hand. Worse,
every op that could unpack (`/`, `}`, `%`) wants its constant in `B`, which is precisely where the
minimum lives. Not a routing problem; there is no arrangement that works.

**A second comparator room does work, and still loses.** Chain two comparator rooms in the ring and
each lap extracts *two* minima — the rooms pipeline, so wall-clock is the slower room's throughput,
not the sum. Worked the protocol out fully (HEAD unbiases its own minimum and ships it after the
marker so TAIL, which owns the output pipe, emits both in order; `-` against `B` rebuilds the bias
token afterwards). ~1.7× on ticks. But a comparator room is ~12×8, and two push the bounding box to
576–676 against 361. Squared, that eats the whole gain and then some.

> [!warning] Parallelism costs rooms, and rooms are what gets squared
> Every scheme that does more per lap needs somewhere to put the extra state, and the only place is
> another room. On `max(w,h)²` that is a losing trade unless the tick win is better than quadratic.

**The win was aspect ratio.** 16 wide × 19 tall charges only the 19, and the input room was sitting
in three rows above HEAD for no reason — only the *pipe* has to be above HEAD to enter its north
wall. Moved the room out into the width slack, reaching over in a single row: **17×17, footprint
289**. Submitted `e457f088-6764-4f8e-a718-882b999a90d3`, 25/25, **786,785** (was 982,801). Leader
457,691, so 2.15× off → **1.72×**.

Ticks did not move at all (2,722.4 both times), which is the cleanest possible confirmation that
this was pure bounding box.

Grid is now square, so the easy geometry is spent — see
[[Selection sort on a ring#Measured]]. Anything further has to remove cells rather than move them.

## 12:10 — input on the west wall: a whole row for nothing

`shrink.py` said the 17x17 was already tight, so the next cut had to be topological. Row 0 existed
only to carry the input pipe over HEAD's north wall. **INPUT does not have to enter from the north** —
it only has to be separated from RING-BACK by [[Nearest pipe resolution]], and the *west* wall
separates them just as well:

```
dist_in(ix,iy) = ix + 1 + iy          (west wall, interior row 0)
dist_rb(ix,iy) = ix + (H - iy)        (south wall, interior col 0)
```

which puts the whole load half (`iy <= 2`) on input and the whole sort half (`iy >= 4`) on the ring,
exactly the split the north wall gave. Column 0 then becomes a riser that costs **no rows at all**,
and the I room drops into the bottom band beside TAIL. 17x17 -> 15x16, **696,945** (was 786,785),
25/25, `acd5b6fb-fcdb-4b7c-822e-01090c174df2`. Ticks unchanged — pure bounding box.

## 12:40 — the return leg does the work: NEW MIN 17 ticks -> 11

The [[Selection sort on a ring#Where the ticks actually go|return bus]] was written up as structural.
It is not; it is a consequence of *where the cycle sits*. With the cycle in the north-west corner
both branch exits point east, away from the entry, so NEW MIN walked tail + riser + the whole bus.

Slide the 8-cell cycle two columns east and the picture changes:

```
        (2,4)>  (3,4)r  (4,4)X1 --marker--> east along row 4
        (2,5)s          (4,5)-
        (2,6)^  (3,6)+  (4,6)X2 --new min-> east, then DOWN
   row 7:  ^  s  W  <  <   <------------------ home, westbound
```

NEW MIN drops one row and runs **west along row 7 doing `W s + M` on the way**, then climbs column 1
straight into the entry corner: **11 ticks against KEEP's 5**, where it used to be 17.

Two things fell out for free:

> [!note] A tie needs no code of its own
> When `t == min`, "adopt t and send the old min back" and "keep min and send t back" are the *same*
> register moves: `W` on `A=0, B=min` gives `A=min, B=0`; `s` sends `min` (which *is* `t`); `+` gives
> `A=min`; `M` sets `B=min`. So TIE just falls into the NEW MIN lane one cell along. The `<+^`
> detour is gone and X2 needs no third handler.

> [!note] `+ W s` is one instruction shorter than `W s + M`
> `A = t-min, B = min` -> `+` gives `A=t` -> `W` gives `A=min, B=t` -> `s` sends the old minimum and
> `B` is already the new one. No `M` at all. (Not shipped — with this routing the freed cell is a
> turn either way, so it is worth 0 ticks here. Worth remembering for a different lane.)

7/7 local, 1723 -> 1522 avg ticks, and **615,004** on the server (25/25),
`sort-numbers-615004-newmin-lane-16x16.man`. Rank 19/82, leader 316,351.

## Where the remaining ticks are, and why they did not move

Per `n = 16` round the cycle is now at its floor:

| | ticks | note |
| --- | --- | --- |
| KEEP, 8 cells x ~136 token visits | ~1090 | **floor** — see below |
| MARKER + PROLOGUE, 23 x 16 passes | ~370 | 7 instructions, **16 ticks of travel** |
| NEW MIN, +6 x ~50 | ~300 | was +12 |
| LOAD, 8 x 16 | ~130 | floor, same argument |

**8 cells is the floor for the compare cycle and it is a counting argument, not a layout one.** The
cycle needs `r X - X + s`: four non-turning instructions and two `X`es. A grid cycle has even length;
a 2x3 cycle has 4 corners and only **2** edge cells, so it cannot hold four non-turning ops. 3x3 has
4 corners (the two `X`es plus two plain arrows) and exactly 4 edges. There is no 7-cell cycle.

The marker's 16 ticks of travel are what is left, and they resisted every rearrangement: X1's marker
exit is forced east, the emit `s` is forced into the east column band, and the adopt path's riser can
only use a column that is free on rows 4 **and** 5 — with the marker lane occupying `ix 5..8` of row
4 and the prologue `ix 10..12`, that is `ix 9` and nothing else, which fixes the bus at 7 cells.
Breaking it needs one more free column, i.e. a wider HEAD, which is the packer's call and not ours.
