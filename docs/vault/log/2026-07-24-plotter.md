# plotter — Bresenham on the LM-75

32×24 [[Display assignments|display-judged]] problem, one Bresenham segment per
[[Rounds|round]], ≤20 rounds per case, 6 public cases, footprint-tick scoring. Standings `best`
was 25,857,000 at 02:40, 23,733,405 by 03:30 — a soft target, so correctness first.

## The one-token Bresenham

Prior work (scratch `verify_math.py`) had already found the trick and validated it over all
589 824 endpoint pairs: pack the error accumulator and the pixel address into **one** integer,

```
token = 1024 * err + addr          (addr ∈ [0,768) so the low 10 bits are the address)
emit  token & 1023
token += (token >= 0) ? dq : dm
```

with, for `d=|Δx|`, `a=|Δy|`, `mn=min(d,a)`, `mx=max(d,a)`:

```
dm     = (mn<<11) + step_m
dq     = (mn<<11) - (mx<<11) + sx + sy32
token0 = (mn<<11) - (mx<<10) + 32*y0 + x0
```

`step_m` is `sx` when x dominates and `sy32` otherwise; `sx+sy32` is sort-invariant so only
`step_m` needs the comparison. Two extra facts that make it cheap:

- the loop runs exactly `mx` updates, and **the branch is taken exactly `mn` times** — so both
  the always-adder and the cross-adder are plain [[Bounded loop with the backpack|counted loops]],
  no data-dependent termination anywhere (verified exhaustively, `design.py`).
- `X` is the only comparator, and the sign of the packed token *is* the Bresenham test — no
  subtraction needed in the hot loop.

## Machine shape

| room | registers | job |
| --- | --- | --- |
| IN | — | 4 × `r`,`s`: pushes x0 y0 x1 y1 into the queue |
| SETUP | A, B + FIFO | ~140-tick straight-line program, emits 5 constants |
| ECHO | BP | the FIFO turnaround, and the router for the last five pushes |
| P | A=token, B=dm, BP=mx | emit, count, `X` on sign, add dm or bounce through Q |
| Q | B=dq, BP=mn | cross-step adder |
| EMIT | B=1023 | `&` → ADDR, then `` `15` `` → DATA |

**The FIFO-as-third-register**: a little man has only A and B, but Bresenham's setup needs a
dozen live values. SETUP therefore owns one pipe out to ECHO and one pipe back, and the pair is
a queue: `s` is push, `r` is pop, and a `r`,`s` pair rotates the front to the back for 2 ticks.
Rooms cannot loop a pipe back to themselves ("ends at the first arrowhead whose forward cell is
on a room border, **any room other than the source**"), so the turnaround needs ECHO.

**Nearest-pipe discipline**: this is the real layout constraint. `s`/`S` only see outgoing pipes
and `r`/`R`/`U`/`q` only see incoming ones, so a room may hold one of each without ambiguity —
but a big room with two outgoing pipes cannot keep `s` honest across a 45-cell snake. Fix: give
SETUP exactly **one pipe in and one pipe out**, deliver the round's input *through the queue*
(room IN pushes it), and take the results out through the queue as well. ECHO does the routing:
the number of pushes per round is a **constant** (every `X` arm pushes the same number of
values, by construction), so ECHO forwards a fixed count back to SETUP and then routes the last
five — two to Q, three to P.

## Verified along the way

- Display plumbing (`exp1.man`): ADDR 0 / DATA 15 / SWAP 0 commits one white pixel. Confirms the
  runner's device against the spec.
- Drawing engine (`stage1.man`): P/Q/EMIT with hardcoded constants drew 8 of the 9 pixels of
  (3,4)→(9,12) — every pixel correct, the ninth lost because the SWAP arrived before the last
  DATA. **Ordering rule**: `L_swap > L_token→EMIT + 9 + L_data − 3`.
- ADDR/DATA sync: one man sends both, 9 ticks apart, so `L_addr ≈ L_data + 9`; the window is a
  whole pixel period (~14 ticks), so it is forgiving. Getting it wrong smears pixels one cell to
  the right — the cursor auto-advance writing at the stale cursor.

### Room programs (all verified in stage1 except SETUP/ECHO)

```
P  y1: > s d 0 s _ v        Q  y1: > r + s m d v
   y2: _ _ m _ _ _ _           y2: ^ _ _ _ _ < _
   y3: _ v X + v _ _           y3: ^ _ M r b r <
   y4: _ v < _ v _ _           y4: @ _ _ _ _ _ ^
   y5: _ > s r v _ _
   y6: ^ < < < < _ _        EMIT y1: @`1023`M .. > r & s _ _ v
   y7: @ _ _ _ _ _ v             y2:               ^ s `51` <
   y8: ^ r M r b r <
```

`d` doubles as the loop's corner (clockwise while `BP>0`, straight out when the count runs
out) — the counter costs one cell, not a branch. In P the `X` arms are: `A>0` west into the
cross path, `A<0` east onto `+` (add dm), `A=0` south onto a `<` that merges into the west path,
so `s`(→Q) and `r`(←Q) each appear exactly once.

### The layout that remains

Nearest-pipe resolution is the whole difficulty and the rule that makes it tractable is:
**`s` only ranks outgoing pipes and `r` only ranks incoming ones**, so a room with one of each is
free of ambiguity. SETUP (1 in, 1 out) and ECHO's reads (use `R`, receive-from-any) are therefore
safe. ECHO's three *outgoing* pipes need geometry: put the ECHO→SETUP source on the wall at the
snake's own end and the →P/→Q sources on the perpendicular wall past it, so the x-terms cancel and
the test reduces to `2·row < tail_row + 2` — satisfied for every snake row, violated for every
tail row.

Remaining: place display / SETUP / ECHO / P / Q / EMIT / input on one canvas and route the nine
pipes without crossings. Two timing constraints to honour, both measured in stage1:

- `L_addr ≈ L_data + 9` (one man sends both, nine ticks apart)
- `L_swap > L_(P→EMIT) + 9 + L_data − 3`, else the last pixel misses its frame.

### Three bugs found during assembly

1. **`snake.py` reversed numeric literals for westward runs.** It does not need to: `` `123` ``
   walked right-to-left reads *321*, i.e. the digits come out in the order the man meets them, so a
   literal is written in walk order regardless of direction. The reversal turned `L32` into 23 and
   silently produced `dm`/`dq` nine too small. Fixed in `lit()`.
2. **ECHO can use `R` for every receive**, which deletes the incoming-pipe geometry problem
   entirely: only one of its two incoming pipes ever has data at a time (round N+1's input is
   withheld until the frame commits). That leaves only the three *outgoing* pipes to place —
   SETUP under the loop row on the bottom wall, P and Q above their own tail rows on the top wall.
3. **Q must test `d` before its `r`.** With `mn == 0` (horizontal, vertical and single-pixel lines)
   the cross step never happens; a Q that received first blocked forever, jammed the ECHO->Q pipe
   and deadlocked every later round. This was the whole 16/20 -> 20/20 delta.

## Optimisation passes

**Pass 2 — ECHO's forward loop (15.4M -> 12.5M).** A tick-profile over `one pixel` showed SETUP
blocked 214 of 460 ticks while ECHO was blocked 5: ECHO was the bottleneck, not SETUP. The reason
is that a counted loop's *return leg costs as many ticks as its body*, so a 1-pair body
(`R s m d`, 4 cells) costs ~10 ticks per value, not 4. Unrolling to five `R s` pairs per turn
(41 = 1 + 8x5) drops it to 5.2 ticks/value. Fixed round cost 499 -> 345.

> [!note] General rule
> For a boustrophedon counted loop, ticks per item = `2*(2k+2)/k` for `k` unrolled items —
> 10 at k=1, 6 at k=2, 5.2 at k=5, 4.5 at k=8. Unroll until the row runs out of width.

**Pass 3 — slide the band left (12.5M -> 10.6M).** Nothing was wrong with 60x54; the left band
just started at x=2 and EMIT took its input pipe on its *left* wall. Since EMIT has exactly one
incoming pipe its position is unconstrained, so that moved to the bottom wall and the whole band
went hard against x=0: **56x54, footprint 3136**. Submission `476d8891-b327-4c2a-9c4e-db3335fde96a`,
**score 10,604,698 = 3,136 x 3,381.6 ticks, rank 1/39.**

### Pass 5 — tick work (8,289,216 -> 6,321,946, avg 3,597.8 -> 2,743.9)

Rooms run concurrently, so the per-pixel cost is the max over rooms and the per-round cost is
the critical path. Three separate wins:

1. **ECHO's forwarding loop returns loaded.** The old boustrophedon paid its walk-back for
   nothing (5.0 ticks/value at k=5). Filling the return row with `R s` pairs too gives
   **2.5 ticks/value** — 4 eastward passes and 3 westward of six pairs = 42, + 1 on the reload
   row = 43. `a` closes the loop because the turn wanted is counter-clockwise.
2. **Q's cross-step ring 16 -> 10 cells.** What actually matters is not the ring length (Q sits
   blocked on `r` anyway) but the `r`->`s` gap, so `+` sits directly between them.
3. **P's ring 20 -> 14 (cross) / 8 (add).** Restored the **no-zero bias** — `addr0 += 1024`
   with the error scaled by two, so `tok = 2048*err + 1024 + addr` is never 0 and `X` becomes a
   pure two-way branch whose *both* arms are ring corners. The cross arm is deliberately long:
   six cells separate the send to Q from the receive, so the pipe-Q-pipe round trip finishes
   while the man is still walking and **P never blocks**.

> [!note] `d`/`a` gives BP0 passes, not BP0+1
> Turns = BP0-1, loop-body executions = BP0. P's `m` runs *before* its test, so its counter has
> to start at **mx+1** (`1 M R +` on the init row) to still emit mx+1 pixels and apply mx
> updates. Getting this wrong drops the last pixel of every line.

> [!warning] A faster P needs a longer SWAP pipe
> Once P's ring is quicker than EMIT's 14, EMIT is up to three pixels behind when P sends its
> last token, and the SWAP overtakes the last DATA -> silent frame mismatch. The pipe is now
> **50 cells**: `L_swap > 3*14 + 12`.

> [!warning] Check *every* room in `pipecheck.py`, not just the ones you edited
> Moving the ECHO->P port to column 12 made one of ECHO's *forwarding* `s` cells tie with it
> (both Manhattan 8) and reading order handed the value to P — so P's init read `x0` as its
> first constant. Symptom was `ADDR 1023`. Fixed by moving ECHO's SETUP port one column east.
